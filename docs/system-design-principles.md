# 系统设计原则

状态：正式原则

本文定义项目在系统设计与功能实现中必须长期遵守的高层原则。新功能、重构和问题修复都应以这些原则作为设计与评审依据。具体页面规范、视觉样式和技巧表现必须建立在这些原则之下，不得替代或绕过这些原则。

## 1. UI 必须由主题驱动

所有具有设计含义的颜色、字体、尺寸、间距、圆角、线宽、透明度和动画参数，都必须来自主题中的语义令牌。

业务组件和具体功能中不得使用临时颜色、任意固定数值或局部自定义视觉方案。根据运行时容器尺寸计算出的布局结果不属于设计硬编码，但参与计算的设计基准仍应由主题或统一设计系统提供。

## 2. 业务语义与视觉表达必须分离

领域层只描述业务事实和状态，不描述颜色、形状、尺寸或动画。

视觉层根据统一的语义状态和当前主题决定具体表现。业务规则的变化不应要求修改主题，视觉风格的变化也不应侵入业务逻辑。

## 3. 同一概念必须只有一个标准模型

同一个业务概念在游戏、提示、提示实验室、回放和交互推理中，必须使用统一的数据结构、状态定义和解释规则。

不为不同入口长期维护并行协议、兼容模型或重复实现。展示形式可以不同，但语义来源必须唯一。

## 4. 状态与具体渲染方式必须解耦

系统先确定对象处于什么状态，再由对应的渲染器决定如何显示。

同一状态可以根据设备、布局或场景使用不同的几何表现，但不能复制或重新解释业务状态。不同渲染器必须消费同一份标准状态结果。

## 5. 问题必须通过系统集成方案解决

发现问题时，应先定位它所属的系统层级，再从共享模型、主题、状态解析器、公共组件或统一接口中解决，不得通过某个页面、某个技巧或某个条件分支增加临时补丁。

一个合格的系统集成方案应当：

- 解决当前问题及同类问题。
- 自动覆盖所有使用相同基础设施的功能。
- 明确各模块的职责和集成边界。
- 删除被替代的旧实现，避免长期并行。
- 通过端到端回归验证整体行为。
- 使未来新增功能自然继承正确规则，而不需要复制修复代码。

这一原则可以概括为：

> 优先修复系统，而不是修饰现象；优先建立统一能力，而不是累积局部例外。

## 6. 应用内功能图标必须优先采用统一的标准图标库

启动器图标、商店图标及其他承载产品品牌识别的图形属于品牌资产，应独立设计，不受本条限制。除此之外，导航、工具栏、按钮、状态和提示等应用内功能图标，默认使用 [Google Material Symbols](https://fonts.google.com/icons) 的官方图形；当前产品以 `Outlined` 风格作为首选，以保持轻量、清爽且一致的视觉语言。

选择和实现图标时必须遵守以下规则：

- 先按功能语义在官方图标库中查找准确图标，不因实现方便自行近似绘制，也不以 Unicode 字符、文字字形或另一套图标库替代已有的合适图标。
- 使用官方矢量路径、字体字形或受统一封装的官方资源，保留其标准轮廓、比例、开口方向和内部留白；颜色、尺寸和容器对齐可以由主题调整，但不得随意改造路径形状。
- 同一界面及同一功能族不得无原则混用不同图标体系。已有 Material Symbols 能表达语义时，不新增自定义版本。
- 官方库没有合适语义、平台规范明确要求其他图标，或功能需要独有品牌表达时，才允许自定义；例外必须在对应设计文档中说明原因，并按现有图标的线宽、视觉重量和尺寸完成评审。
- 图标名称不能代替面向用户的语义。所有可操作图标仍需提供本地化的无障碍名称，并在必要时提供状态或长按行为说明。
- 验收时应与 Google 官方示例核对实际渲染结果，而不只检查代码中的图标名称；重点检查轮廓、方向、视觉重量及选中、禁用、显示和隐藏等状态是否正确。

新增或替换应用内图标时，应优先扩展统一图标组件，使后续页面自然继承相同来源与渲染规则，而不是在业务页面内重复保存或绘制图标。
