# Hard Sudoku Pro：技巧成长系统开发计划

状态：开发方案初稿，先冻结协议与指标，再以算法可靠性决定是否继续产品化

记录日期：2026-09-02

关联产品规划：`docs/technique-growth-product-plan.md`

题库覆盖与定向补题：`docs/technique-content-coverage-strategy.md`

## 1. 文档目的

本文档把已经确认的技巧成长产品方向拆分为可独立开发、测试和验收的工程模块。实施顺序固定为：

```text
明确目标
  ↓
冻结协议和指标
  ↓
算法/识别核心验证
  ↓
实验室可靠性门槛
  ↓
影子存储与真实游戏验证
  ↓
产品化可靠性门槛
  ↓
成长档案与正式存储
  ↓
成长界面
  ↓
互动反馈
  ↓
Beta 校准与发布验收
```

在协议、指标和识别口径没有冻结前，不得先制作正式成长页面或动画。界面不得通过临时字段反向决定领域数据结构，算法也不得直接写入用户可见文案。

## 2. 开发目标与边界

### 2.1 首轮目标

- 使用现有 39 项技巧代码形成稳定、可升级但不过度版本化的成长数据协议。
- 在不阻塞正常游戏的前提下，识别高可信技巧机会及玩家对机会的处理结果。
- 记录有效遇到、推定独立发现、提示影响和有效发现时间。
- 从原始事实生成可重算的技巧档案、成长曲线和生命周期。
- 提供首页摘要、成长总览、技巧详情和完成页成长反馈。
- 在验证打扰边界后，增加有限、可关闭的游戏内轻反馈。
- 全部个人成长数据保存在本地，无网络时完整可用。

### 2.2 首轮核心策略

首轮坚持“高可信、低覆盖”：

> 只统计提示引擎能够明确识别，且玩家动作与技巧结果准确匹配的机会；宁可漏记，也不把不确定动作错误归入某项技巧。

算法阶段不再把 `HintEngine.nextStep()` 的单一选择视为完整机会真值。C++ 核心先提供最低等级完整前沿，并进一步提供可分步、可恢复的当前盘面直接机会搜索；现有 `nextStep()` 只保留为提示选择兼容接口。多机会算法必须先通过独立验收，才允许行为匹配、正式存储、成长页面或互动反馈接入。

### 2.3 指标能否支持预期效果

现有指标从产品表达上已经覆盖首轮成长效果：

- “遇到多少次、独立完成多少次、使用多少次提示”能够描述接触与独立性。
- 初期、近期和最佳有效时间能够形成从慢到快的成长曲线。
- 稳定性、题目多样性和数据可信度能够避免一次偶然成功被夸大成掌握。
- 生命周期能够把 39 项技巧整理为待探索、正在成长、已掌握和待巩固。
- 结构化指标能够支持完成页总结和克制的鼓励反馈，而不必伪造一个绝对能力分数。

因此，当前缺口不是再增加更多用户可见指标，而是证明这些指标的输入事实可靠。只要“这次动作是否对应某个技巧、是否独立、计时是否有效”识别错误，成长曲线、掌握状态和鼓励动画都会放大错误结论。

### 2.4 核心可行性门槛

本系统的核心不是存储或曲线绘制，而是用户行为识别及其评价。实施采用明确的继续/停止门槛：

1. TG-0 冻结协议、事实定义和算法评价方法。
2. TG-1/TG-2 只实现 Hint Lab 原型、回放夹具、反例和实验室评价报告。
3. TG-2 未通过时，停止游戏接入、正式存储、成长页面和互动反馈开发；可以继续改进识别算法，但不得把实验结果呈现为玩家能力结论。
4. TG-2 通过后，只允许进入 TG-3/TG-4 的影子存储和真实游戏验证，不向玩家显示成长结论。
5. TG-4 再以真实试玩抽样复核误判、漏记、污染和性能。只有产品负责人通过第二次可靠性门槛，才进入 TG-5 至 TG-7 的成长档案、界面和互动反馈。

这一门槛优先保证低误判。覆盖不足意味着成长出现得慢，可以继续优化；错误归因会破坏信任，不能由漂亮的界面补救。

### 2.5 非目标

- 不在本计划中增加第 40 项技巧。
- 不建设课程、考试、证书、排行榜或群体比较。
- 不上传棋盘、逐动作历史或个人技巧档案。
- 不使用猜测、回溯或答案反推技巧。
- 不用一个不透明的 0–100 分替代可解释指标。
- 不允许成长模块失败阻止玩家填数、暂停、保存或完成游戏。

## 3. 一级模块划分

系统分为五个一级产品开发模块和两个支撑模块。

| 编号 | 模块 | 核心责任 | 主要输出 |
| --- | --- | --- | --- |
| M1 | 协议与指标 | 定义机会、事件、档案、生命周期、兼容边界和统计口径 | 纯 TypeScript 合同与规则测试 |
| M2 | 存储 | 保存原始事实、会话状态、可重算汇总和反馈回执 | SQLite migration 与仓储接口 |
| M3 | 算法/识别核心 | 识别机会、维护分析候选、匹配动作、处理提示和歧义 | 高可信成长事件 |
| M4 | 成长界面 | 呈现总览、详情、曲线、首页和完成页摘要 | 只读 ViewModel 与页面组件 |
| M5 | 互动反馈 | 分级、延后、合并、限频和播放鼓励反馈 | FeedbackCandidate 与调度状态 |
| S1 | 应用编排 | 把游戏命令流、识别、存储和页面状态连接起来 | TechniqueGrowthController |
| S2 | 调试与测试 | Hint Lab、影子运行、fixture、性能和人工验收 | 可审计证据与验收报告 |

模块编号表示长期职责边界，不等同于实现顺序。M2 存储必须依赖 M1 协议，但正式冻结表结构前应先用 M3 的 Hint Lab 原型证明识别数据确实可产生；因此 TG 阶段先做识别可行性，再完成正式 migration。

依赖方向固定为：

```text
UI / 互动反馈
      ↓
应用编排
      ↓
协议与指标 ← 算法/识别核心
      ↑              ↓
      └────────── 存储接口
```

领域协议不得依赖 React Native、SQLite 或原生模块；UI 不得直接读取 SQLite；识别核心不得生成本地化文案或播放动画。

## 4. M1：协议与指标

M1 是所有后续模块的前置门槛。首批代码建议位于：

```text
src/domain/technique-growth/
  contracts.ts
  opportunity.ts
  metrics.ts
  lifecycle.ts
  feedback.ts
  index.ts
```

### 4.1 首版开发期版本策略

当前处于首次公开发行前的开发期。协议必须保留未来升级能力，但首版开发过程中不维护多个兼容分支：

- 只维护一套当前协议、当前识别策略和当前 profile 规则，设计变化直接更新当前基线和测试。
- 不为每次字段、阈值或算法调整分别增加 Contract、Opportunity、Profile、Feedback 版本。
- 算法实验使用 Git commit、构建号或配置指纹记录可复现性，不把实验编号当作永久数据兼容版本。
- TG-2 通过且进入正式存储时，持久化记录可保留单一 `formatVersion` 升级入口；首版开发期保持为同一个值，破坏性调整允许重建内部测试数据。
- 首个发行候选冻结时，再确定首个公开协议和成长模型基线。公开发行后，只有需要读取、迁移或重新解释已发行数据时才增加版本并提供迁移。

原则是“保留升级入口，不提前维护历史”。原始事实一旦随公开版本发行就不能静默改写；发行前的实验事实不承担永久兼容义务。

### 4.2 核心协议

建议的首版领域对象：

```ts
type TechniqueOpportunity = {
  id: string;
  sessionId: string;
  puzzleId: string;
  techniqueCode: TechniqueCode;
  boardRevision: number;
  boardFingerprint: BoardFingerprint;
  result: TechniqueResultSignature;
  startedActiveMs: number;
  confidence: 'high' | 'ambiguous';
};

type OpportunityOutcome =
  | 'independent'
  | 'hint_viewed'
  | 'hint_applied'
  | 'superseded'
  | 'ambiguous'
  | 'interrupted'
  | 'invalidated';

type TechniqueGrowthEvent = {
  formatVersion: number;
  id: string;
  opportunityId: string;
  techniqueCode: TechniqueCode;
  outcome: OpportunityOutcome;
  discoveryMs: number | null;
  sourceMoveId: string | null;
  recordedAtEpochMs: number;
};

type TechniqueLifecycle =
  | 'unexplored'
  | 'growing'
  | 'mastered'
  | 'needs_refresh';
```

`TechniqueResultSignature` 只保存匹配动作所需的填数或候选排除，不把完整 `HintStep` 和全部证明正文复制到长期事件表。

### 4.3 指标目录

第一版冻结以下事实指标：

| 指标 | 定义 | 是否直接展示 |
| --- | --- | --- |
| 有效机会数 | 符合当前机会策略并正式关闭的高可信机会数量 | 是 |
| 推定独立发现数 | 未查看或应用提示，动作准确匹配技巧结果 | 是 |
| 提示查看数 | 机会期间打开了对应智能提示 | 是 |
| 提示应用数 | 机会结果由智能提示实际应用 | 是 |
| 歧义/失效数 | 无法可靠归因、撤销、错误或盘面重建造成失效 | 仅诊断 |
| 有效发现时间 | 从机会开始到准确匹配动作的游戏有效时间差 | 是 |
| 初期典型时间 | 最早一组有效独立样本的中位时间 | 是 |
| 近期典型时间 | 最近一组有效独立样本的中位时间 | 是 |
| 最佳有效时间 | 未受暂停、提示、错误污染的最短时间 | 是，不能单独决定掌握 |
| 稳定性 | 近期样本离散程度 | 首版可只用于规则 |
| 题目多样性 | 有效样本来自多少道不同题目 | 可用于可信度 |
| 数据可信度 | 根据样本量、歧义、题目多样性和新鲜度确定 | 是 |

初期和近期窗口的具体样本数在 Beta 前冻结。最长时间不作为主要成长指标；暂停、后台、广告和长时间无操作不计入有效发现时间。

这些是产品成长指标，不同时承担算法评价职责。算法是否可信必须使用第 5.6 节的独立质量指标评估，不能用“曲线看起来合理”代替识别验收。

### 4.4 成长派生指标

成长曲线和生命周期只能由事实指标派生：

- 时间改善：初期典型时间与近期典型时间的差异。
- 独立率：推定独立发现数 ÷ 可用于独立性判断的有效机会数。
- 提示依赖度：提示查看或应用占有效机会的比例。
- 当前稳定性：近期独立结果与时间波动。
- 数据可信度：低、中、高或等价的可解释状态。

“已掌握”至少同时考虑样本数量、独立率、提示依赖、稳定性、题目多样性和数据新鲜度。一次最佳时间不得直接进入掌握状态。

### 4.5 M1 完成门槛

- 所有协议为纯 TypeScript，不依赖 UI、数据库或原生实现。
- 39 项 `TechniqueCode` 均可进入同一通用协议，不存在技巧专用字段分叉。
- 序列化和反序列化可以验证当前格式、枚举和时间范围，并为未来格式迁移保留单一入口。
- 指标公式、样本不足、歧义和生命周期转换具有确定性测试。
- 所有尚未冻结的阈值以策略配置表达，不散落为魔法数字。

## 5. M3：算法与识别核心

识别核心是整个系统的技术重点，建议位于：

```text
src/application/technique-growth/
  opportunity-analyzer.ts
  technique-growth-session.ts
  action-matcher.ts
  growth-candidate-state.ts
```

### 5.1 技巧机会分析器

本阶段首先验收 C++ 纯算法内核，不实现应用层调度。算法接口满足：

- `frontierOnly` 分步扫描最低非空等级的全部候选，与现有提示结果兼容。
- `allDirect` 在同一不可变盘面上继续扫描配置等级内的直接机会，不推演执行步骤后的未来搜索树。
- 一个确定性工作单元运行一个技巧检测器；暂停和恢复使用会话内部游标，不以毫秒作为算法协议。
- 任意工作单元分片的最终机会集合、顺序、证明和 `humanCost` 必须与一次性搜索相同。
- 会话复制棋盘、候选和 given-cell 数据；独立会话互不共享搜索状态。单个高级检测器仍是一个原子工作单元，并保留既有深度、节点和候选数量边界。
- 取消、非法盘面、非法配置和终局均为显式终态，不输出未完成检测器的结果。

机会评价使用两层稳定身份，不使用证明页面或 detector 返回序号充当身份：

- **动作结果（outcome）**：排序、去重后的 placements 与 eliminations；用于判断一个玩家动作是否存在多种技巧解释。
- **机会身份（identity）**：`technique + outcome`；同技巧、同动作但来自不同行、列、宫或不同证明路径时折叠为一个机会，同时保留证明变体数量。
- **原子效果（effect）**：单个 placement 或 elimination；即使两个 outcome 不完全相同，只要共享一个 effect，玩家执行该动作时仍可能存在多机会或多技巧归因。

选择遮蔽只描述算法可观测事实：未选中的同级机会标记为“被前沿排序遮蔽”，更高等级机会标记为“被低等级遮蔽”。不同技巧产生完全相同 outcome，或者仅共享一个 effect 时，分别记录完整结果歧义和原子动作歧义；不在本层强行推断玩家使用了哪项技巧，也不把遮蔽分类直接换算为掌握分数。

单个 effect 的纯算法归因固定为四种结果：

| 结果 | 判定 | 是否输出技巧候选 |
| --- | --- | --- |
| `noMatch` | 当前机会集合没有 identity 包含该 effect | 否 |
| `uniqueTechnique` | 仅一个 identity 包含该 effect | 是 |
| `sameTechniqueMultipleOpportunities` | 多个 identity 包含该 effect，但 technique 相同 | 是，保留全部 identity |
| `crossTechniqueAmbiguous` | 至少两个不同 technique 包含该 effect | 否，必须保守放弃 |

这里的“唯一”只相对于输入的有界机会集合成立，不等于玩家独立发现。任一相关检测器达到枚举边界时，应用层不得把该结果升级为可靠成长事件；需要扩容复算或保守放弃。即使没有边界风险，技巧候选仍须经过后续动作序列、提示状态、自动铅笔、撤销和时间窗规则，才能进入行为识别。

每个完成的检测器输出候选数量和 `reachedEnumerationLimit`。默认边界继续保护现有提示延迟；算法评价可以显式提高边界，并要求扩容结果包含全部默认 identity。当前39技巧夹具的4个唯一风险盘面中，扩容新增12个 identity（`forcingNet` 2个、`xyChain` 10个），证明默认 `allDirect` 不能被描述为无界完整搜索。

本阶段明确不实现 React Native 桥接、后台线程、revision、玩家动作匹配、存储、成长评分和界面。算法验收通过后，`TechniqueOpportunityAnalyzer` 才作为后续适配器把原生机会压缩为领域对象：

```ts
interface TechniqueOpportunityAnalyzer {
  analyze(
    request: GrowthAnalysisRequest,
    options?: { signal?: AbortSignal },
  ): Promise<TechniqueOpportunityResult>;
}
```

要求：

- 在后台执行，不能阻塞 UI。
- 绑定 session、revision 和盘面指纹。
- 新操作到达时取消或废弃过时结果。
- 不读取答案后拼接证明。
- 只接受已经通过算法验收的确定性机会集合，不自行补推或改变技巧归因。
- 分析尚未完成时玩家已经继续操作，宁可漏记，不阻止输入。

### 5.2 独立分析候选状态

成长系统维护 `growthCandidates`，与以下状态隔离：

- 玩家手工草稿 `manualCandidates`。
- 快速草稿 `quickCandidates`。
- 瞬时完整候选 `solverCandidates`。
- 智能提示轨迹 `hintCandidates`。

`growthCandidates` 的规则：

- 新盘面从合法候选建立。
- 玩家准确完成已识别排除时更新。
- 填数后清理同行、同列和宫。
- 提示应用后同步结果，但记录为辅助。
- 普通手工候选添加、遗漏或错误不反向污染分析状态。
- 撤销、擦除确定数字、恢复或指纹不匹配时，首版保守重建并关闭旧机会。

它属于成长会话，不加入正式 `GameState`，避免成长功能改变核心游戏规则和既有存档协议。

### 5.3 动作匹配

动作匹配只读取已经被游戏领域引擎接受的前后状态和命令：

- 确定数字与机会 placement 完全一致。
- 候选删除与机会 elimination 一致。
- 多结果技巧是否要求一次完成全部结果，由当前冻结的机会策略决定。
- 使用提示、撤销、错误输入或盘面重建不得记为完全独立发现。
- 多项技巧可解释同一动作时记录歧义，首版不强行归类。

首版不观察 UI 点击，也不把选择格、打开页面或候选自动生成视为技巧完成。

### 5.4 有效计时

机会计时复用游戏有效时间，不建立与游戏规则不同的第二套时钟：

```text
discoveryMs = 动作完成时的 activeElapsedMs - 机会开始时的 activeElapsedMs
```

需要提取可测试的 `activeElapsedAt(gameState, atEpochMs)`。暂停、后台、广告和系统中断自然排除；长时间无操作的额外过滤由机会策略处理。

### 5.5 M3 完成门槛

- 相同盘面的一次性搜索与任意分片、暂停、恢复搜索产生完全一致的有序结果。
- 最低前沿只包含最低非空等级；全直接搜索按配置扫描且不生成未来步骤搜索树。
- 同技巧多位置、同等级多技巧、跨等级共存和相同动作多技巧解释均有专项遮蔽夹具。
- 每个机会具有完整证明和 `humanCost`，结果不重复；取消不接纳当前未完成检测器的结果。
- 39 项现有 Hint Lab fixture 均能生成合法机会签名。
- placement、单项 elimination、多项 elimination、提示、撤销和失效路径有测试。
- 快速连续操作不会应用过期分析结果。
- 相同盘面、候选和当前策略配置产生确定结果。
- 识别失败、取消或超时不影响游戏命令和存档。
- 记录分析耗时、漏记和歧义诊断，但不上传。

### 5.6 算法评价体系

算法评价与用户成长指标分开。评价报告至少覆盖：

| 质量指标 | 评价内容 | 风险优先级 |
| --- | --- | --- |
| 归因准确率 | 被归为某技巧的事件中，人工真值确认正确的比例 | 最高 |
| 独立发现误判率 | 实际受提示、答案、撤销、错误或其他技巧影响，却被记为独立的比例 | 最高 |
| 机会覆盖率 | 真值中存在且符合首轮范围的机会，被分析器识别的比例 | 高，但低于误判 |
| 动作匹配召回率 | 玩家确实完成目标动作时，系统成功关闭并归因的比例 | 高 |
| 歧义与保守放弃率 | 存在多种解释或证据不足时，系统正确放弃归因的比例 | 高 |
| 污染隔离率 | 提示、暂停、后台、撤销、错误、恢复和快速连续输入未污染独立结果的比例 | 最高 |
| 过期结果丢弃率 | revision 或指纹失效的异步分析均未进入事件流 | 最高 |
| 确定性 | 同一输入、构建和配置重复执行得到相同结果 | 必须满足 |
| 分析耗时 | P50、P95、最慢耗时及对输入和保存的影响 | 发布门槛 |
| 技巧覆盖分布 | 39 项技巧分别具备多少正例、反例及成功识别结果 | 发布门槛 |

真值集分四层建立：

1. 已知技巧与结果的 Hint Engine fixture。
2. 带预期玩家动作序列的脚本回放，包括 placement、单项和多项 elimination。
3. 对抗性反例，包括提示中断、先做其他动作、撤销、错误输入、恢复、候选不完整和快速连续输入。
4. 本地影子运行的抽样人工复核；原型阶段只保存调试证据，不建立正式用户画像。

TG-0 必须冻结抽样方法、真值标注规则和每项阈值。具体数值不在未经数据验证时拍脑袋确定，但门槛优先级已经确定：独立发现误判和过期/污染事件必须接近零；覆盖率不足可以作为继续改进算法的理由，不能用放宽归因标准换取。

TG-2 产出逐技巧混淆结果、失败案例目录、性能报告和是否进入影子运行的建议。只有报告可复现、39 项均有证据且产品负责人签字通过，才允许进入 TG-3/TG-4。TG-4 使用真实试玩抽样再次输出同口径报告，只有第二次签收后才允许产品化。任一门槛未通过时，结论只能是“改进算法后复评”或“暂停该功能”，不能先建设正式界面来制造既成成本。

## 6. M2：存储

存储模块建议位于：

```text
src/data/user/technique-growth-repository.ts
src/data/user/technique-growth-serialization.ts
```

实验室可靠性通过 TG-2 后，再在当前首版开发 schema 中建立影子运行所需的独立表。TG-4 通过前，这些记录只服务本机诊断和人工复核，不生成用户可见结论。首版发行前只维护一个当前 schema，不为每次表字段调整累积兼容 migration；开发迁移在发行候选前合并为首个公开基线。

### 6.1 建议数据表

#### `technique_opportunities`

保存机会身份、技巧、盘面 revision、紧凑结果、开始/结束有效时间、outcome 和 confidence。公开发行基线冻结后，如识别语义变化需要区分历史事实，再加入最小必要的模型兼容标识。

#### `technique_growth_events`

保存机会结果、来源 move/event、发现时间和提示影响。来源 move 或 event ID 唯一，保证重试不会重复统计。

#### `technique_growth_session_state`

保存当前分析 revision、紧凑 `growthCandidates` 检查点和开放机会。恢复时无法继续的机会标记为 `interrupted`，不能把离线时间计入发现时间。

#### `technique_profiles`

保存可重算的读取缓存，包括样本数、独立数、典型时间、最佳时间、可信度和生命周期。开发期使用当前 profile 规则重建；公开发行后如规则变化会重新解释用户数据，再增加必要的模型版本。

#### `growth_feedback_receipts`

保存已经展示的里程碑和反馈，避免崩溃、恢复或页面重进时重复庆祝。

### 6.2 持久化原则

- 原始机会和事件是事实来源，profile 是可重建缓存。
- 所有写入使用稳定 ID 和唯一来源事件实现幂等。
- 识别分析与 profile 计算不得阻塞游戏操作事务。
- 成长保存失败进入幂等重试和下次启动对账；最终无法恢复时记录本地诊断并宁可漏记，不能阻止核心游戏保存，也不能伪造事件补齐数据。
- 首版开发期的内部数据库可在明确的破坏性 schema 变化后重建；不得为尚未发行的每个中间 schema 增加永久兼容代码。
- 首个发行候选必须从全新安装和明确指定的 Beta 基线验证升级；公开发行后，数据库升级失败时保留原库并沿用 recovery 规则。
- 初版不自动删除原始成长事件；上线前验证长期数据量后再决定归档策略。
- 重置成长档案必须独立确认，不能清除奖励、题目首次完成或 Premium 权益。

### 6.3 M2 完成门槛

- 当前开发 schema 的全新安装、重建和指定 Beta 基线升级可复现；公开发行后才要求所有受支持的已发行 schema 无损升级。
- 重复写入、崩溃重试和乱序完成不会重复事件。
- 开放机会在杀进程、暂停、恢复和内容版本变化后有确定处理。
- 删除 profile 后能够从原始事件得到相同汇总。
- SQLite 完整性、外键和 required table 检查覆盖新增表。
- 事件量和查询在长期模拟数据下满足启动与页面响应目标。

## 9. M5：互动反馈

建议把反馈决策和动画表现分离：


### 9.1 反馈候选协议

领域层只生成候选：

```ts
type GrowthFeedbackCandidate = {
  id: string;
  level: 'silent' | 'light' | 'important' | 'milestone';
  techniqueCode: TechniqueCode;
  reason: GrowthFeedbackReason;
  metricDelta: GrowthMetricDelta | null;
```

它不决定当前能否播放动画。调度器再根据以下上下文决定立即展示、延后、合并或丢弃：

- 玩家是否连续输入。
- 游戏是否暂停、提示打开或显示弹窗。
- 自动检查是否关闭。
- 本局已经展示的次数。
- 反馈强度设置和系统减少动态效果。
- 事件可信度和是否会泄露动作正确性。

### 9.2 首轮顺序

1. 完成页静态反馈。
2. 完成页可跳过曲线或里程碑动画。
3. 每局最多一次游戏内轻反馈。
4. 丰富、简洁、关闭三档设置。
5. 根据 Beta 数据冻结默认值、时长和冷却。

### 9.3 M5 完成门槛

- 反馈不遮挡棋盘、不阻塞输入、不改变选择或抢焦点。
- 多事件可以合并，恢复后不会重复庆祝。
- 自动检查关闭时默认不即时确认正确动作。
- 减少动态效果提供等价静态内容。
- 玩家可以立即跳过完成页庆祝。
- 动画出现后的输入延迟、误触、关闭率和主观打扰感经过 Beta 验证。

## 10. S2：调试、测试与影子运行

### 10.1 Technique Growth Lab

优先扩展现有 Hint Lab，而不是先建设正式页面。调试界面至少显示：

- 当前机会技巧、revision 和盘面指纹。
- `growthCandidates` 摘要。
- 期望填数或候选排除。
- 机会开始有效时间和当前计时。
- 玩家动作匹配、歧义或失效原因。
- 事件、profile 和反馈候选。
- 分析耗时和取消状态。

### 10.2 影子运行

正式游戏接入后，第一阶段只在本地记录，不向玩家显示掌握和动画。影子运行用于确认：

- 各等级机会数量和技巧分布。
- 39 项技巧实际被识别的比例。
- 匹配成功、漏记和歧义比例。
- 分析 P50、P95 和最慢耗时。
- 快速连续输入造成的过期分析数量。
- 提示、暂停、恢复、撤销和错误的污染情况。

数据只用于本机调试和人工验收，不自动上传。

影子运行结束后必须按第 5.6 节重新生成算法质量报告。TG-4 是进入成长档案、界面与互动反馈的第二道门槛；真实行为数据未通过时，继续改进或暂停识别，不得开放成长功能。

### 10.3 自动化测试层次

1. 协议测试：当前格式、未来迁移入口、序列化、指标和生命周期。
2. 匹配测试：placement、elimination、提示、撤销和歧义。
3. 39 fixture 回放：每项技巧至少一个机会与结果签名。
4. SQLite 测试：migration、幂等、恢复、重算和重置。
5. 应用测试：快速操作、取消、暂停、后台和终局。
6. UI 测试：四语、曲线摘要、生命周期和反馈合并。
7. 真机测试：性能、动画、减少动态效果和屏幕阅读器。

## 11. 分阶段实施步骤

### TG-0：目标、协议与指标冻结

交付：M1 全部合同、成长指标、算法评价指标、当前策略配置、真值标注规则和纯函数测试。

门槛：产品、算法、数据和 UI 后续模块只依赖冻结协议；未决阈值都有明确配置和负责人，不能由页面临时决定；明确算法通过、改进后复评和暂停功能三种结论的签收方式。

### TG-1：识别可行性原型

交付：Hint Lab 中的机会分析、动作匹配、有效计时和 `growthCandidates` 原型；从评级路径与 HSP 运行时路径覆盖报告提取代表性正例、反例和中间状态。

门槛：代表性 placement、elimination、链技巧及反例通过；普通游戏代码尚不受影响。

### TG-2：39 项识别验收

交付：39 fixture 通用机会签名、脚本动作回放、对抗性反例、取消和确定性测试，以及逐技巧混淆、题库机会覆盖与性能报告。

门槛：确认现有 `nextStep()` 是否足够支持首版；算法质量达到 TG-0 冻结阈值并由产品负责人签收。未通过时不进入 TG-3，不够时先形成证据，再决定改进匹配规则、扩展原生引擎接口或暂停功能。

### TG-3：存储与恢复

交付：M2 影子记录所需的 migration、仓储、序列化、幂等和重算测试；此阶段不提供玩家可见 profile。

门槛：当前首版 schema 的全新安装、重建和指定 Beta 基线升级通过；成长失败不阻塞游戏，恢复不会制造虚假用时。发行前合并开发期 migration，不保留无实际兼容对象的历史分支。

### TG-4：正式游戏影子运行

交付：S1 控制器、已接受命令观察、后台分析、调试快照。

门槛：正常游戏无可感知回退；真实试玩样本达到 TG-0 冻结要求，并按与 TG-2 相同口径完成人工复核。算法质量再次由产品负责人签收，未通过则不进入 TG-5。

### TG-5：档案与生命周期

交付：profile projector、可信度、四种生命周期和当前策略配置。

门槛：原始事件可重复得到相同档案；样本不足不产生掌握结论。

### TG-6：成长界面

交付：M4 总览、详情、曲线、首页和完成页静态卡片。

门槛：四语、无障碍、空状态和长期数据量通过；页面不参与领域计算。

### TG-7：互动反馈

交付：M5 分级策略、调度、完成页动画、游戏内轻反馈和设置。

门槛：不阻塞、不泄露、可跳过、可关闭，并通过打扰程度验收。

### TG-8：Beta 校准与发布签收

交付：掌握阈值、样本窗口、默认反馈强度、性能和产品验收报告。

门槛：产品负责人明确批准指标口径和默认体验；首个公开兼容基线冻结；已知误判、性能和恢复问题不阻断发布。

## 12. 首轮必须先决定的问题

TG-0 开始前或过程中必须逐项冻结：

1. 一次多结果 elimination 需要完成全部结果还是任一有效结果才算成功。
2. 打开提示但未翻到结论，是否统一记为 `hint_viewed`。
3. 自动候选和快速铅笔如何影响独立性与可信度。
4. 长时间无操作从计时中排除还是直接使机会失效。
5. 初期与近期典型时间各使用多少有效样本。
6. 数据可信度的低、中、高门槛。
7. 掌握、待巩固和恢复稳定需要多少连续证据。
8. 普通统计重置是否同时重置技巧成长档案。
9. 影子运行出现何种覆盖缺口和性能证据时，才允许从 `nextStep()` 升级为多机会接口。
10. 每局游戏内反馈起始频率和默认反馈档位。
11. 归因准确率、独立发现误判率、机会覆盖率、污染隔离、确定性和性能的 TG-2 通过阈值。
12. 逐技巧真值集最小正例、反例和人工复核样本量。

## 13. 整体完成定义

技巧成长系统只有同时满足以下条件才算首轮完成：

- M1–M5 与 S1–S2 均通过各自门槛。
- TG-2 实验室评价和 TG-4 真实游戏影子评价均通过产品负责人签收；任一未通过则本功能保持实验状态，不以界面完成度替代验收。
- 39 项技巧使用统一协议、页面和存储，不存在按技巧硬编码的旁路。
- 普通离线游戏、提示、恢复和完成流程没有性能或正确性回退。
- 玩家可以理解数据是推定且有可信度，不会把缺少样本误解为不会。
- 成长曲线可以从本地事实重算，升级不会丢失永久里程碑。
- 首版只形成一个公开兼容基线；发行前迭代没有遗留无必要的版本分支和 migration 链。
- 成长反馈带来可验证的成就感，同时不阻塞、不过度打扰、不泄露答案。
- 双平台、四语、动态字体、减少动态效果和屏幕阅读器完成验收。

在整体完成前，可以按 TG 阶段提交可测试的垂直切片，但不能用一个看似完整的静态页面替代核心识别和数据可信度。
