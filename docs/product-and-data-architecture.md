# Hard Sudoku Pro：首期产品与数据架构决策

## 1. 文档目的

本文档记录 Hard Sudoku Pro 首期已经确认的产品边界与技术方向，作为后续设计、开发、题库交付、测试和发行的共同依据。

本文档重点记录基础架构、题库管理、答案存储、提示引擎和多语言要求。具体游戏页面、交互、本地统计、广告、购买和额度奖励规则记录在 `docs/game-feature-plan.md`。

## 2. 首期范围

### 2.1 目标平台

- Apple iPhone（iOS）。
- Android 手机。
- 使用 React Native 开发，当前项目版本为 React Native 0.87.1。

### 2.2 题库来源

- 题库内容由专人在 App 发行前提供。
- App 不提供在线题库管理后台。
- App 运行期间不从服务器下载、同步或热更新题库。
- 题库只能随着新版本 App 的发布而更新，以降低开发和长期维护成本。

### 2.3 首期非目标

- 不建设题库更新服务器或同步服务。
- 不支持运营人员在 App 发布后远程增加、删除或修改题目。
- 当前不设计具体游戏内容、页面和玩法细节。
- 当前不把本地成绩视为具有防作弊能力的竞技成绩。

## 3. 总体数据架构

题库数据和用户数据应使用两个相互独立的 SQLite 数据库。

| 数据库 | 主要内容 | 生命周期 |
| --- | --- | --- |
| `content.sqlite` | 题目、答案、难度、来源、题库版本等发行内容 | 随 App 版本发布，可被新版题库整体替换 |
| `user.sqlite` | 做题进度、完成记录、用时、设置和语言选择等用户数据 | App 升级时保留，并通过数据库 migration 演进 |

将两个数据库分开的主要原因：

- 更新题库时不会覆盖用户进度。
- 题库可以作为经过验收的只读发行物处理。
- 用户数据库可以独立备份、迁移和排查问题。
- 数据职责清晰，降低升级逻辑和后期维护难度。

应用代码应通过统一的数据访问层读取题库，不应让页面组件直接执行 SQL。

### 3.1 首版开发期的版本策略

当前项目处于首次公开发行前的开发期，尚不存在必须长期兼容的公开用户数据基线。首版架构需要支持未来升级，但不为每次内部字段、表结构、题库重建或算法调整制造一个新版本：

- 开发期只维护当前 `content.sqlite`、`user.sqlite` schema 和领域协议基线；有意的破坏性调整可以重建开发数据和 fixture。
- 保留稳定 ID、数据访问层、migration 入口、生成清单和校验值，使首个公开版本冻结后能够安全升级。
- `content_version`、schema version、rating/model version 表示真实的发行或数据语义兼容边界，不等于构建次数、提交次数或实验次数。
- 重复生成验证题库使用可丢弃产物或同一个明确的开发基线，不因每次生成而增加产品内容版本；已经提交或标记为不可变审计/发行产物的版本不得覆盖。
- 发行候选前合并无外部兼容对象的开发期 migration，形成首个公开基线；发行后才对已经交付用户的数据实施版本递增、迁移和兼容测试。

当项目进入第二版或任何公开发行后的开发阶段时，必须先在 `AGENTS.md` 更新当前发行状态和需要兼容的基线，再开始改变持久化格式。这样保留升级能力，同时避免首版开发历史演变成永久兼容负担。

### 3.2 匿名产品分析决策（已决策，暂缓实现）

产品保持“核心玩法完全离线可用”的定位，同时允许未来在不影响游戏的前提下收集匿名产品分析数据，用于观察 D1、D7、D30 留存和关键功能使用情况。离线能力与产品分析相互独立：没有网络、分析服务不可用或用户关闭分析时，启动、游戏、提示、保存、恢复和本地统计都必须保持正常。

未来首选方案为 Google Analytics for Firebase，初始采用 Firebase Spark 免费方案，只启用 Analytics：

- 不绑定账单账户，不启用 Blaze 方案。
- 不启用 BigQuery 导出、Cloud Functions、Firestore 或其他可能产生费用的云服务。
- 通过项目自己的 `AnalyticsService` 抽象接入，业务和页面不得直接依赖 Firebase SDK，以便替换供应商或退回无操作实现。
- Analytics 初始化、事件记录和上传必须异步、允许失败，不得成为任何游戏流程的前置条件。
- 使用随机生成的安装实例标识理解匿名留存；在没有账号系统时，它不代表自然人，重新安装、清除数据或更换设备可能形成新的安装实例。

首期留存口径预定为：以 `first_open` 所在日期形成新增安装 cohort，D1、D7、D30 分别表示该安装实例在首次启动后的第 1、7、30 个自然日再次活跃。正式实施前需固定时区、迟到事件和重复事件的处理规则，避免不同平台报表口径不一致。

为满足留存和早期产品判断，未来只采集最小事件集合，例如 `first_open`、`session_start`、`game_started`、`game_completed`、`game_abandoned`、`level_selected`、`hint_used` 和 `quick_pencil_used`。不得上传棋盘内容、答案、逐步操作历史、用户输入文本、通讯录、精确位置或广告标识符。是否增加事件必须经过产品价值和隐私必要性审核。

设置页未来应提供“匿名使用数据”开关，并支持在适用地区先禁用收集、完成必要的告知或同意后再启用。实现时必须同步完成 App Store 隐私标签、Google Play Data Safety、隐私政策、第三方依赖和数据保留规则审核。

本节只冻结产品和架构方向，当前不引入 Firebase SDK、不创建生产 Analytics 数据流，也不改变现阶段开发范围。实际接入必须作为独立任务再次批准。

### 3.3 公开网站决策

发行前建设一个使用自有域名、托管在 Cloudflare 静态托管服务上的最小官方网站。网站只承担公开信息和商店合规职责，不建设应用后台、账号系统、数据库、内容管理系统或动态 API，也不改变 App 的离线架构。

首期网站范围固定为：

- 首页：游戏简介、品牌素材、必要截图和 App Store、Google Play 下载入口。
- 隐私政策页：提供商店审核和 App 内隐私入口所需的长期稳定 URL。
- 支持页：提供联系邮箱和精简常见问题。
- 使用条款页：可以在 Premium、广告或其他商业化能力上线前补齐。

网站默认不使用 Cookie、第三方追踪或网站分析，不作为首期付费安装广告的必经落地页。广告素材、商店页面和 App 内体验的 A/B 测试分别使用广告平台、App Store Connect、Google Play Console 和未来独立批准的产品分析方案；初期广告可直接进入对应商店页面，避免增加“广告→网站→商店”的转化步骤。

如果未来需要 SEO 内容、媒体资料、活动落地页、网页 A/B 测试、Cookie 或网站分析，应作为网站范围扩展单独决策，并同步复核隐私政策和同意要求。

## 4. 题库数据库

### 4.1 建议的最小数据结构

以下结构仅表示首期需要保存的核心信息，最终 schema 可在正式开发时进一步确定：

```sql
CREATE TABLE puzzles (
  id TEXT PRIMARY KEY,
  puzzle TEXT NOT NULL,
  solution TEXT NOT NULL,
  difficulty_level INTEGER NOT NULL CHECK (difficulty_level BETWEEN 1 AND 5),
  difficulty_score INTEGER NOT NULL,
  hardest_technique TEXT NOT NULL,
  rating_version TEXT NOT NULL,
  source TEXT,
  content_version INTEGER NOT NULL,
  checksum TEXT NOT NULL,
  enabled INTEGER NOT NULL DEFAULT 1
);
```

字段原则：

- `id` 是题目的稳定标识，一经发行不应因排序或重新导入而改变。
- `puzzle` 使用固定 81 个字符表示题面，空格建议用 `0` 表示。
- `solution` 使用固定 81 个字符表示完整答案。
- `difficulty_level` 保存展示给用户的数字等级 `1` 至 `5`。
- `difficulty_score` 用于同一等级内的排序和难度校准，不直接展示给用户。
- `hardest_technique` 保存评级求解路径中必需的最高技巧代码。
- `rating_version` 标识产生当前评级的规则和求解器版本。
- `source` 用于记录题目来源或供应批次。
- `content_version` 标识题库内容版本。
- `checksum` 用于完整性和重复性检查，不作为安全加密手段。
- `enabled` 允许在不立即删除历史数据的情况下停止分配某道题。

如果未来需要题包、主题、作者或分类，可以新增独立表，不必在首期预先设计所有可能字段。

开发期这些字段保持当前基线并随设计一起更新，不为尚未发行的中间状态保留并行解释器。首个发行候选冻结后，`content_version` 才成为对外不可变的内容身份；`rating_version` 也只在评级语义发生需要区分或重算发行数据的变化时增加，而不是随每次代码修改增加。

### 4.2 题库交付与生成

建议由内容提供者提交约定格式的 CSV、JSON 或 SQLite 文件，再通过构建脚本生成最终的 `content.sqlite`。不建议直接把未经自动验证的人工文件放入安装包。

推荐流程：

1. 内容人员按照固定的数据规范提交题目。
2. 构建脚本执行格式、合法性、唯一解和重复题检查。
3. 验证全部通过后生成最终 `content.sqlite`。
4. 将数据库作为 App 安装包资源发布。
5. App 首次启动时将其复制到应用私有数据目录并以只读方式使用。

当前仓库中的100道候选题只用于验证生成、评级、验收和数据库构建流程，不是正式发行题库。正式发行目标为总计 `10,000–30,000` 道通过全部自动检查和人工抽检的离线题目；若安装包体积与内容质量允许，可以继续增加。Level 1–5 的正式数量和比例在上线前根据评级结果确定，不在当前阶段固定。

移动 App 只需要保存题面、答案和精简评级元数据。完整生成日志、审计报告和大体积解题路径保留在构建产物中，不随 App 分发，以避免题量增加时无谓扩大安装包。

#### HoDoKu2 离线生成决策

首期正式采用 HoDoKu2 `2.4.3 build 116` 作为离线候选题生成器、答案求解器和逻辑路径分析器。固定 JAR、配置、许可证与评级规则保存在 `tools/puzzle-generator/`，但不进入 React Native App 安装包。

HoDoKu2 的原始五级标签只负责产生不同难度的候选池。项目最终的 `difficulty_level` 由完整逻辑路径中最高的 HSP 技巧等级决定，HoDoKu2 累计分数保存为 `difficulty_score`，只用于同级排序。构建流程同时保存原始输出和版本校验值，保证结果可以审计。

### 4.3 发行前自动验证

每次生成题库至少应检查：

- 题面和答案都恰好包含 81 格。
- 字符只包含约定的数字和空位表示符。
- 题面中的已知数字与答案一致。
- 答案的每一行、每一列和每个九宫格都合法。
- 每道题有且只有一个解。
- 不存在重复题目。
- 每个 `id` 唯一且稳定。
- 题目可由项目支持的逻辑技巧完整解出，不需要猜测或回溯。
- 难度等级、分数、最高技巧和评级版本均有效。
- 题库 schema 版本和内容版本均有效。
- 最终数据库可在 iOS 和 Android 构建中正常打开和查询。

内容提供者可以提交预期等级和预期技巧，但正式等级必须由项目自己的统一评级器计算。提供方等级与系统等级不一致时，题目应进入人工复核，不能直接采用提供方标签。

发行前还应评估一项技巧覆盖质量目标：冻结的 39 项技巧是否各有至少 50 道可玩题目。该目标目前是阶段 8 的待确认门槛，不在当前开发阶段强制执行。自动统计时，一道题只有在统一评级器的完整标准路径中至少产生一次该技巧的有效步骤，并且运行时提示引擎能够从对应状态复现，才计入该技巧；同一道题可以计入多项技巧，但对同一技巧最多计数一次。

构建报告应为每项技巧输出独立题目数、步骤总数、所属等级分布和可复现结果。若某项不足 50 题，应优先补充或重新筛选候选题，并进行人工试玩，不得通过重复题、等价变换题或降低逻辑质量来凑数。上线前还需决定“每项至少 50 题”是正式发布阻断门槛，还是用于题库组合优化的质量目标；仅在标准路径中偶然出现，也不等同于适合作为该技巧的代表性练习题。

覆盖必须区分两套语义：`puzzle_technique_usage` 表示 HoDoKu2 标准评级路径；构建期另由 HSP C++ `nextStep()` 全量回放导出运行时标准路径。前者用于评级审计和候选检索，后者用于成长算法样本与补题优先级。两者都不保证真实玩家一定遇到该技巧；如果某技巧检测器已有正例、但始终不被 `nextStep()` 选中，应先评价机会选择算法，不能直接归因于题库不足。

`puzzle_technique_usage` 需要以 `(technique_code, rating_version, puzzle_id)` 建立反向索引，并由内容数据层提供包含任意或全部技巧、难度、最少使用次数及数量限制的参数化检索。详细执行规则见 `docs/technique-content-coverage-strategy.md`。

### 4.4 基于解题技巧的难度体系

#### 4.4.1 评级原则

题目等级应由“完整解出题目所必需的最高技巧等级”决定，再使用技巧出现次数和总解题步骤计算工作量分数，用于校准同一等级内的相对难度。

不能只用题目给定数字的数量判断难度；也不能只统计最高技巧而忽略解题路径。一道只需要一次高级技巧的题，与一道需要大量中高级步骤的题，实际体验可能明显不同。

推荐公式为：

```text
最终等级 = 完整解题所需的最低技巧等级上限
同级排序 = 各技巧权重乘以使用次数后的累计分数
质量复核 = 自动评级 + 人工试玩抽检
```

#### 4.4.2 首版五级技巧建议

以下分组作为首版起点，正式权重和边界应根据题库样本与人工试玩结果校准：

| 显示等级 | 允许且可能必需的最高技巧 | 预期体验 |
| --- | --- | --- |
| 1 | 最后一格、唯一候选数、隐性唯一候选数 | 入门，可通过直接观察完成 |
| 2 | 宫区交互、指向数、区块排除、显性数对、隐性数对 | 基础逻辑 |
| 3 | 显性/隐性三数组、四数组、X-Wing | 中高级，通常需要完整候选数 |
| 4 | XY-Wing、XYZ-Wing、Swordfish、Skyscraper、Two-String Kite、简单染色 | 高级技巧 |
| 5 | Jellyfish、XY-Chain、AIC、复杂染色、强制链等 | 专家级 |

技巧难度具有一定主观性，不同求解体系对技巧顺序和名称可能有不同定义。部分技巧也可以用其他技巧体系表达。例如 Skyscraper 可以被视为 Turbot Fish 或 X-Chain。因此，项目必须固定自己的技巧代码、定义、所属等级和检测顺序，不能在同一评级版本内随意改变。

首期规则：

- 所有 Level 1 至 Level 5 题目都必须能用项目支持的逻辑技巧解出。
- 猜测、试错和通用回溯算法不属于 Level 5 技巧。
- 回溯算法只能用于验证唯一解，不能用于计算展示给用户的难度。
- 超出当前逻辑求解器支持范围的题目不能进入正式题库。
- Level 5 的技巧边界应在收到首批题目后复核，避免范围过宽或题量不足。

#### 4.4.3 自动评级流程

评级器应按固定顺序从简单技巧开始，并逐级启用技巧：

```text
验证题目格式和唯一解
        ↓
只启用 Level 1 技巧，尝试完整求解
        ↓ 未解出
启用 Level 1–2 技巧，从原题重新求解
        ↓ 未解出
依次增加 Level 3、Level 4、Level 5
        ↓
记录能够完整解题的最低等级
        ↓
记录完整求解轨迹、最高技巧、技巧次数和累计分数
```

求解器必须遵守以下确定性要求：

- 每一步始终优先检查较简单的技巧。
- 同一状态存在多个可用步骤时，使用固定的技巧顺序和格子顺序。
- 每次评级相同题目都应产生一致结果。
- 不能因为某一步可以使用更高级技巧，就人为提高本来可由低级技巧解出的题目等级。
- 应保存求解轨迹或轨迹摘要，保证评级结果可以审计和复现。

#### 4.4.4 技巧权重和工作量分数

每种技巧应配置：

- 稳定的 `technique_code`。
- 所属等级。
- 评级器中的检测顺序。
- 工作量权重。
- 多语言显示名称和说明所使用的翻译键。

题目分数可以采用以下基础模型：

```text
difficulty_score = Σ（技巧权重 × 使用次数）
```

最高技巧决定最低等级，累计分数可以把题目提升到更高等级，或用于同级排序，但具体阈值不应在缺少真实题库样本和试玩数据时过早固定。

为了保留每道题的评级依据，建议增加技巧使用明细表：

```sql
CREATE TABLE puzzle_technique_usage (
  puzzle_id TEXT NOT NULL,
  rating_version TEXT NOT NULL,
  technique_code TEXT NOT NULL,
  use_count INTEGER NOT NULL,
  PRIMARY KEY (puzzle_id, rating_version, technique_code)
);
```

如果需要保存完整解题轨迹，可在构建产物中保留独立的评级报告，而不必把所有步骤放入面向用户的运行时数据库。

#### 4.4.5 评级版本管理

技巧等级属于项目定义，并非永久不变的客观标准。每套规则必须使用独立版本，例如：

```text
rating_version = "hsp-1.0"
```

发生以下变化时必须提升评级版本，并重新评定全部题目：

- 增加、删除或重新定义技巧。
- 调整技巧所属等级。
- 调整技巧检测顺序。
- 修改技巧权重或等级分数阈值。
- 修复会改变解题路径或结果的求解器错误。

同一 App 版本内只能采用一套正式评级规则，避免相同题目在没有明确原因时显示不同等级。

#### 4.4.6 题库验收报告

构建流程应为每道题生成可供内容人员和测试人员检查的报告，例如：

```text
题目 ID：puzzle-00128
提供方等级：4
系统等级：4
最高技巧：XY-Wing
总逻辑步骤：63
技巧使用：
  Hidden Single × 24
  Locked Candidates × 8
  Naked Pair × 3
  XY-Wing × 1
唯一解：通过
评级版本：hsp-1.0
```

每个等级都应抽取足够题目进行人工试玩，重点检查系统评级与真实玩家感受是否一致，以及同一级别内是否存在明显的难度跳跃。

汇总报告还应增加 39 项技巧的覆盖矩阵，至少列出每项技巧覆盖的唯一题目数、总出现次数和可供人工抽检的题目 ID。若采用每项至少 50 题的目标，人工抽检应特别确认稀有技巧不是仅作为可绕过的偶然步骤出现。

#### 4.4.7 用户展示与多语言

首期主要向用户显示跨语言一致的数字等级：

```text
Level 1
Level 2
Level 3
Level 4
Level 5
```

在题目详情、帮助或技巧教学中，可以额外显示该等级可能需要的技巧。技巧名称使用稳定代码和翻译键管理，例如：

```json
{
  "technique.xWing": "X-Wing",
  "technique.hiddenPair": "Hidden Pair"
}
```

英语、日语、德语和简体中文的技巧名称应由熟悉数独术语的人审核。部分高级技巧在不同地区缺少统一译名，必要时可保留英文名称作为副标题。

### 4.5 可解释的逐步提示引擎

#### 4.5.1 功能目标

提示功能不是直接显示答案，而是基于玩家当前棋盘状态，用人类能够理解的逻辑技巧逐步解释下一步。一次完整提示需要支持：

1. 高亮相关行、列、宫、格子和候选数，并指出所使用的技巧。
2. 标出可以排除的候选数或可以确定的数字，并解释推理原因。
3. 经用户确认后应用结果，并将操作加入撤销历史。

这一能力需要系统内置“可解释的人类逻辑求解器”。只读取 `content.sqlite` 中的完整答案，或者使用只返回最终答案的回溯求解器，无法产生可靠的技巧依据和逐步讲解。

#### 4.5.2 两类求解能力

系统应区分两个用途不同的模块：

| 模块 | 用途 | 是否直接用于用户提示 |
| --- | --- | --- |
| 精确求解器 | 唯一解验证、题库检查、检测无解状态 | 否 |
| 人类逻辑求解器 | 难度评级、寻找下一步技巧、生成提示和技巧教学 | 是 |

精确求解器可以在内部使用回溯算法；人类逻辑求解器只能使用项目正式定义的 Level 1 至 Level 5 技巧。数据库答案可以辅助识别错误输入或验证完成状态，但不能替代逻辑推理过程。

#### 4.5.3 构建时与运行时职责

题库构建时生成的标准解题路径可用于评级、验收和测试，但不能直接作为运行时的唯一提示来源。玩家可能采用不同顺序、已经完成部分标准步骤、只填写部分候选数，或者在中途输入错误数字。

推荐采用混合模式：

- 构建题库时生成标准求解轨迹和评级报告。
- App 运行时根据玩家当前棋盘重新寻找下一条可解释步骤。
- HoDoKu2 只在构建期负责出题、评级、生成审计轨迹和充当正确性对照，不进入 App 安装包。
- App 内的运行时提示引擎使用适合商业分发的宽松许可证实现，并通过原生模块在 iOS、Android 上离线运行。
- 构建期与运行时可以采用不同实现，但必须共享项目定义的技巧代码、技巧语义、等级、检测优先级和 `HintStep` 数据契约。
- 玩家在提示的任一阶段修改棋盘后，当前提示立即失效并重新计算。

#### 4.5.4 结构化提示结果

求解器不能直接生成中文、英文等自然语言文本，而应返回与语言和界面无关的结构化结果，例如：

```ts
type HintStep = {
  techniqueCode: 'lockedCandidates.pointing';
  difficultyLevel: 2;
  focusCells: CellRef[];
  focusRegions: RegionRef[];
  premiseCandidates: CandidateRef[];
  eliminations: CandidateRef[];
  placements: Placement[];
  explanationKey: 'hint.lockedCandidates.pointing';
  explanationParams: {
    digit: number;
    box: number;
    row: number;
  };
};
```

同一份 `HintStep` 应同时驱动：

- 棋盘区域、关键格子和候选数高亮。
- 排除数字或确定数字的动画。
- 三阶段提示内容。
- 英语、日语、德语和简体中文解释。
- 自动应用和撤销操作。
- 单元测试和提示结果快照测试。

例如“指向数”技巧不应只返回“删除候选数 7”，而应同时描述作为前提的宫、行、候选位置，以及所有可排除位置。

#### 4.5.5 分页式动态证明提示交互

智能提示保留观察、推理、结论三个语义阶段，但页面数量由结构化证明决定；简单技巧可以没有
独立推理页，高级技巧可按证据组、链接或分支展开多个推理页。

第一阶段为“观察方向”：

- 告诉用户当前建议使用的技巧。
- 高亮相关区域、关键格子和构成推理依据的候选数。
- 不显示最终需要排除或填写的结果。

第二阶段为“推理结果”：

- 使用另一种视觉状态标出可排除候选数或确定数字。
- 显示推理原因。
- 暂不自动修改棋盘。

第三阶段为“应用结果”：

- 删除对应候选数或填入确定数字。
- 播放简短且可关闭的反馈动画。
- 将全部变化作为一个原子操作加入撤销历史。
- 记录本题使用提示的次数和阶段。

三阶段必须来自同一个不可变的 `HintStep`，展示层再从该结构生成分页内容。提示期间棋盘只读并保持可见：背景变暗，无关格子弱化，相关格子、候选数以及行、列或宫使用底色与轮廓高亮；排除项还应使用删除线、斜杠或图标，避免只靠颜色传达信息。

底部抽屉显示本地化技巧名称、说明、分页状态以及“上一个 / 下一个 / 应用”操作。前两阶段和关闭操作不修改盘面，只有最后的“应用”会执行结果。一次提示从首个有效页面展示时扣除 1 个额度，翻页和应用不得重复扣费，中途关闭不退还。如果棋盘版本发生变化，旧提示不能继续应用。

#### 4.5.6 玩家草稿与系统候选数

系统应维护四个不同概念：

- `manualCandidates`：初始为空、由玩家自行录入和编辑的手工草稿。
- `quickCandidates`：快速铅笔生成后由玩家继续编辑的快速草稿。
- `solverCandidates`：根据当前确定数字重新计算的完整合法候选集合，是瞬时基础数据，用于生成快速草稿和重建提示状态。
- `hintCandidates`：提示引擎已经建立并通过逻辑步骤继续维护的候选状态，随游戏会话持久化，只用于智能提示推理。

`manualCandidates` 与 `quickCandidates` 都是玩家草稿，编辑行为相同，但来源不同。`solverCandidates` 是由确定数字直接推导的瞬时完整候选集合，不能在后台持续覆盖玩家已经编辑的快速草稿。`hintCandidates` 是与玩家草稿完全独立的内部逻辑状态；手工或快速草稿的添加、删除、遗漏和错误都不能改变它，也不能成为提示证明的前提。

`hintCandidates` 的生命周期固定如下：

1. 第一次请求智能提示时，以当时的 `solverCandidates` 初始化，并绑定当前81格确定数字的盘面指纹。
2. 智能提示应用候选排除后，立即更新并持久化 `hintCandidates`，使下一次提示从已经证明的状态继续，避免重复同一排除。
3. 填入新的确定数字时，在现有 `hintCandidates` 基础上删除该格及同行、同列、同宫中受其约束的候选数，然后绑定新的盘面指纹。
4. 通过普通擦除或替换删除已有确定数字时，旧候选状态可能缺少需要恢复的候选数，因此从新盘面的 `solverCandidates` 重新建立 `hintCandidates`；通过撤销返回旧盘面时，则恢复该操作保存的 `hintCandidates` 快照。
5. 游戏保存、退出和继续时必须连同盘面指纹保存并恢复 `hintCandidates`。盘面指纹相同且状态有效时继续使用，不能重新初始化。

智能提示应用的排除可以同步删除两份玩家草稿中已经显示的对应候选数，以保持界面一致，但这只是输出同步：玩家随后如何编辑两份草稿，都不能反向影响 `hintCandidates`。

游戏会话还应保存：

- `activeCandidateSource: 'manual' | 'quick'`：当前显示哪一份草稿。
- `pencilMode: boolean`：数字键当前编辑候选数还是填写确定数字。
- `quickDraftBoardFingerprint`：快速草稿最后确认有效时对应的确定数字盘面。
- `quickDraftGenerated: boolean`：本题是否存在可恢复的快速草稿。
- `hintCandidates`：智能提示持续推理使用的候选状态。
- `hintBoardFingerprint`：`hintCandidates` 当前对应的确定数字盘面。

首次生成快速草稿后，`activeCandidateSource` 设为 `quick`，`pencilMode` 设为 `true`。关闭快速铅笔只把来源切换为 `manual`，不删除 `quickCandidates`；关闭铅笔只改变输入模式，不隐藏当前草稿。

关闭快速铅笔时保存当前快速草稿和盘面指纹。再次开启时，如果当前81格确定数字的内容指纹相同，就免费恢复用户编辑后的 `quickCandidates`；如果不同，旧草稿视为过期，必须经用户确认并消耗一个额度后，从当前 `solverCandidates` 重新生成。盘面修改后又完整撤销到原内容时，指纹相同，应允许免费恢复。候选数编辑、选择、高亮、暂停和退出不影响指纹。

重新生成必须采用“先计算、后替换、再扣费”的原子流程。用户取消、广告失败、盘面冲突、无解或计算失败时，不得覆盖旧快速草稿，也不得扣除额度。继续未完成游戏时，两份草稿、当前来源、铅笔模式和盘面指纹都必须恢复。

确定数字造成的自动候选数清理应同步作用于两份玩家草稿，并与填数作为同一个可撤销操作。智能提示应用的有效候选排除也应同步作用于两份草稿。

#### 4.5.7 提示前的状态检查

每次请求提示时应按以下顺序处理：

1. 检查行、列和宫内是否有重复数字。
2. 检查当前输入是否让题目变为无解。
3. 如果产品启用了错误检查，识别与标准答案冲突的用户输入。
4. 恢复或初始化与当前盘面指纹匹配的 `hintCandidates`。
5. 从最低等级技巧开始寻找可用逻辑步骤。
6. 返回第一个确定、有效且可解释的 `HintStep`。

如果自动检查已经标出错误数字，或当前棋盘已经无解或存在冲突，不应继续提供正常技巧提示，而应先引导用户修正标红数字、检查冲突或撤销错误步骤。该状态不消耗提示额度。

#### 4.5.8 提示选择策略

提示引擎应与难度评级器使用相同的“简单技巧优先”策略：

- 优先返回当前可用的最低等级技巧。
- 同级技巧按照固定顺序选择。
- 同一棋盘状态应稳定返回同一个优先提示。
- 提示不得使用高于题目正式评级且并非必需的技巧来制造难度。

每次智能提示只完成一个最简单的原子逻辑步骤。原子步骤必须由一个技巧和一套完整、可独立验证的推理依据组成，其结果可以是填入一个确定数字，也可以只是排除一个或多个候选数；候选数排除本身就是有效且完整的提示结果。系统不能为了保证每次提示都填入数字，而把多个连续排除或多个不同技巧合并成一次提示。

提示引擎应先按由简单到复杂的顺序检测当前成立的逻辑步骤，再用标准答案校验填数和候选排除的安全性。不能先读取某个空格的答案，再通过试错、回溯或事后拼接规则为该答案制造解释。标准答案只作为错误识别、结果校验和测试依据，不作为提示证明的前提。

技巧检测器应返回推理依据和结果，而不是直接修改棋盘。界面只有在第三阶段并获得用户操作后才应用结果。

#### 4.5.9 双引擎与稳定契约

构建期和运行时不强求复用同一份求解器代码。HoDoKu2 使用 GPL-3.0，适合独立的离线内容工具；直接把它链接或移植到计划闭源发行的商业 App，可能产生整体开源义务并增加 iOS 集成成本。因此首期采用“双引擎、同一规范”：

```text
项目技巧规范 + HintStep v1
   ├── HoDoKu2（构建期）
   │     ├── 生成和评级
   │     ├── 标准轨迹与验收报告
   │     └── 运行时结果的对照验证
   └── App 提示引擎（运行时）
         ├── 当前盘面动态提示
         ├── 三阶段讲解与技巧教学
         └── iOS / Android 完全离线运行
```

两套实现可能对同一状态选择不同但都正确的下一步，这不属于错误；验收重点是步骤合法、解释完整、技巧分类一致且不使用猜测。正式题库只能包含“构建期评级所需技巧属于运行时引擎支持集合”的题目，防止出现能够评级却无法提示的题目。

#### 4.5.10 运行时开源方案决策

目前没有可以零修改直接安装到 React Native、同时满足完整技巧解释、iOS/Android 离线运行、宽松许可证和禁止猜测的成熟库。首选评估对象为 Apache-2.0 许可证的 `jkomoros/sudoku`：它已经定义结构化 `SolveStep`，包含技巧、目标格、目标数字、依据格和依据数字，并提供禁止猜测的 `NoGuess` 选项。项目应固定一个经过审计的 fork，强制关闭猜测并通过 `gomobile bind` 生成 Android AAR 和 iOS XCFramework，再由一个很薄的 React Native 原生模块返回项目自己的 `HintStep v1`。

候选方案的定位如下：

| 项目 | 定位 | 决策 |
| --- | --- | --- |
| [HoDoKu2](https://github.com/wyzelli/Hodoku2)（GPL-3.0、Java） | 技巧完整的生成、评级和对照工具 | 仅构建期使用，不打包进 App |
| [jkomoros/sudoku](https://github.com/jkomoros/sudoku)（Apache-2.0、Go） | 已有结构化人类技巧步骤 | 运行时首选评估基线，需 fork、审计和补测 |
| [HappyCerberus/sudoku](https://github.com/HappyCerberus/sudoku)（MIT、C++） | 非猜测求解与性能参考 | Go 方案不能满足技巧覆盖时再评估 |
| [sudoku-core](https://github.com/kcirtapfromspace/sudoku-core)（MIT、Rust） | 跨平台结构化提示参考 | 项目过新且存在 Backtracking 回退，首期不直接采用 |
| [Kermalis/SudokuSolver](https://github.com/Kermalis/SudokuSolver)（Zlib、C#） | 技巧证明和测试参考 | 不作为首期移动端运行时 |

任何候选库中的 `Guess`、`Backtracking`、`Trial and Error` 或等价回退都必须从用户提示路径中删除。回溯只允许在构建期验证唯一解，不能生成展示给用户的技巧、说明或难度。

React Native 层只负责状态和展示，不直接实现高级技巧：

```text
当前盘面和题目约束
        ↓
原生人类技巧引擎：校验、重建候选数、从简单到复杂寻找一个步骤
        ↓
HintStep v1：技巧、依据格、作用区域、排除项或填数、证明参数
        ↓
React Native：高亮、分页说明、动画、本地化、应用和撤销
```

标准答案可以校验错误输入、完成状态和提示结果，但不能代替逻辑证明。提示引擎必须基于当前盘面独立推出步骤；不能先读取答案再伪造一个看似合理的技巧解释。

#### 4.5.11 运行时提示验收

每种技巧至少需要覆盖以下自动化测试：

- 可以正确识别该技巧的棋盘状态。
- 相似但不满足条件时不会误识别。
- 高亮区域和推理依据完整且正确。
- 排除或填写结果正确。
- 应用结果后盘面保持合法。
- 四种语言所需的解释参数齐全。
- 相同盘面状态产生确定且可复现的提示。

除此之外，运行时引擎必须通过以下发行门槛：

- 对全部正式题目和抽样的合法中间盘面回放提示，直到完成。
- 每个填数结果必须等于标准答案；每个候选排除都不能排除该格的答案。
- 使用 HoDoKu2 作为离线对照时，不要求两者选择同一步，但要求双方步骤都合法且技巧映射符合项目规范。
- 对玩家采用不同正确顺序形成的盘面做随机路径测试，不能依赖预存的标准解题序号。
- 同一状态必须稳定返回相同步骤，并始终优先选择当前可用的最低级技巧。
- 在目标最低支持设备上测量延迟；求解在后台线程执行，不阻塞 React Native UI。
- 当前状态没有受支持的人类技巧时，应返回明确的“暂无支持的逻辑提示”，不能回退到猜测或直接答案。

提示引擎是题库质量、技巧教学和实际游戏体验共同依赖的核心能力，应作为独立领域模块开发，而不是作为页面组件中的临时逻辑。

## 5. 简单题目生成辅助工具

### 5.1 定位与范围

项目包含一个独立目录：

```text
tools/puzzle-generator/
```

该目录用于规划一个只为 Hard Sudoku Pro 准备发行题目的离线辅助工具。它不是完整的出题系统，不承担题库运营、内容审批、在线服务或发行管理职责，也不会被打包进 iOS/Android App。

当前阶段只建立目录和职责边界，不编写具体生成、求解或评级代码。实现语言、算法和数据格式需要在后续评审中确定。

### 5.2 核心目标

工具只负责三件事：

1. 生成合法的数独题面。
2. 生成并验证题目的唯一答案。
3. 按项目约定的技巧等级，将题目评价为 Level 1 至 Level 5。

最小工作流程为：

```text
生成完整终盘
  -> 移除部分数字形成题面
  -> 检查题目是否只有一个答案
  -> 评价解题所需技巧和难度
  -> 输出题面、答案和难度等级
```

### 5.3 计划输入与输出

计划输入：

- 需要生成的题目数量。
- 目标难度等级或等级分布。
- 用于复现生成结果的随机种子。
- 评级规则版本。

每道题计划只输出最基本的信息：

```text
id
puzzle
solution
difficultyLevel
difficultyScore（可选，只用于同级排序）
hardestTechnique
ratingVersion
```

输出格式可以在 JSON、CSV 或 SQLite 中选择，但当前阶段不做决定。生成结果以后再通过独立的简单步骤放入 App 使用的 `content.sqlite`。

### 5.4 目录框架

```text
tools/
  puzzle-generator/
    README.md
    generation/       # 题面和唯一答案生成职责
    difficulty/       # Level 1–5 难度评价职责
    output/           # 生成结果存放位置
```

当前各目录只有职责说明，没有可执行实现。

### 5.5 明确的非目标

- 不建设题库管理后台。
- 不支持在线题库更新或同步。
- 不设计供应商数据导入适配器。
- 不设计复杂的人工审批和运营流程。
- 不负责发行题量筛选和题库组合管理。
- 不实现复杂的结构等价题检测。
- 当前不实现 SQLite 导出器或综合报告系统。
- 当前不编写生成器、求解器或评级器代码。

### 5.6 与 App 提示功能的边界

题目生成辅助工具只输出题面、唯一答案和难度评价。App 中根据玩家当前棋盘进行区域高亮、候选数排除和逐步技巧讲解，属于独立的运行时提示功能。

两者未来可以共享技巧名称和难度规则，但当前不要求共用同一个代码包。是否共享具体实现，应在开始编码前另行评审，避免为了未来复用而过早增加工具复杂度。

## 6. App 更新时的题库处理

题库虽然不支持在线更新，但仍需要处理 App 升级带来的本地数据库替换。

建议流程：

1. 安装包中携带当前版本的 `content.sqlite` 和内容版本号。
2. App 启动时比较安装包题库与本地题库的版本。
3. 如果安装包版本更高，先完成文件校验，再原子替换本地 `content.sqlite`。
4. `user.sqlite` 始终保留，不随题库替换而删除。
5. 用户进度通过稳定的 puzzle `id` 与题目关联。

如果新版题库删除或停用某道题，建议保留对应历史记录，但不再将该题分配给用户。这样可以避免用户已经完成的统计突然消失。

## 7. 本地答案与安全性

### 7.1 已选择的方向

首期在 `content.sqlite` 中同时保存题面和完整答案。这是目前离线运行、降低开发与维护成本目标下最合适的方案。

这样做可以简化：

- 提示功能。
- 输入纠错。
- 完成状态校验。
- 自动化测试和题库验收。
- iOS 与 Android 的一致性实现。

### 7.2 可提取性的含义

具备一定技术能力的用户可能从 App 安装包或应用数据中提取题库和答案。主要影响包括：

- 用户可以绕过正常游戏过程查看答案。
- 完整题库可能被批量复制。
- 本地完成记录或本地排行榜可能被修改。
- 如果题库本身具有较高商业价值，可能涉及内容授权和知识产权风险。

即使数据库不保存答案，用户仍然可以提取题面并用公开的数独求解器计算答案。因此，只删除答案字段不能提供真正的保密能力。

SQLite 加密或代码混淆只能提高提取门槛。只要 App 必须离线读取数据，解密能力也必须存在于设备上，无法对熟悉逆向工程的用户实现绝对保密。

### 7.3 首期安全边界

- 数据库放在应用私有目录，不提供用户导出功能。
- 首期不为答案引入服务器或复杂加密方案。
- checksum 只用于校验完整性，不应被描述为加密或防篡改保证。
- 如果以后提供有奖金或实际价值的竞技排名，需要重新设计服务器端校验，不能信任本地成绩。
- 在签署题库授权协议时，应确认内容供应方是否允许题面和答案随离线 App 分发。

## 8. 多语言支持

### 8.1 首期语言

| 语言 | Locale |
| --- | --- |
| 英语 | `en` |
| 日语 | `ja` |
| 德语 | `de` |
| 简体中文 | `zh-Hans` |

本文档暂将“中文”定义为简体中文。繁体中文应作为独立语言 `zh-Hant` 处理，需要独立翻译和测试，不能简单视为简体中文的显示变体。

### 8.2 多语言架构

数独题目由数字组成，不需要为每种语言建立一份题库。语言资源必须与 `content.sqlite` 分离。

建议目录：

```text
src/
  localization/
    index.ts
    locales/
      en.json
      ja.json
      de.json
      zh-Hans.json
```

建议使用：

- `i18next` 和 `react-i18next` 管理翻译键、插值和回退。
- `react-native-localize` 检测设备首选语言并匹配受支持语言。

语言行为：

- 第一次启动时跟随设备首选语言。
- 如果设备语言不受支持，回退到英语。
- 设置中允许用户手动切换语言。
- 用户选择保存在 `user.sqlite`，优先级高于设备语言。
- 切换语言后立即生效，不要求重启 App。

### 8.3 文案管理原则

- 组件中不得硬编码用户可见文本。
- 数据库和业务代码只保存稳定代码，例如 `easy`，界面通过翻译键显示“Easy”“初級”“Einfach”或“简单”。
- 按钮、弹窗、错误消息、提示、帮助文本和无障碍标签都必须本地化。
- App 名称、权限说明等 iOS/Android 原生文案需要分别配置。
- App Store 和 Google Play 的商店介绍、截图文案属于独立的发行本地化内容。
- 翻译应由人工审核，尤其是候选数、提示、撤销和难度等数独术语。

### 8.4 界面设计约束

- 德语文案通常比英语更长，按钮和弹窗不能依赖过窄的固定宽度。
- 日语、中文和拉丁字符都需要进行真机字体和截断测试。
- 日期、时间和数字格式应遵循设备区域设置。
- 数独棋盘固定使用数字 `1` 至 `9`，不随界面语言转换为其他数字字符。

## 9. 当前技术方向

当前项目为 React Native 0.87.1。正式实现 SQLite 时，可优先评估 `react-native-nitro-sqlite`，原因包括：

- 支持现代 React Native 架构。
- 同时提供同步和异步查询接口。
- 支持 iOS 和 Android 应用数据目录。
- 较大查询和批量操作可放到异步路径，避免阻塞 UI。

正式引入依赖前仍需完成 iOS/Android 真机验证、维护状态检查和许可证确认。

首期应用标识固定为：

```text
iOS Bundle ID:          com.jackli717.sudoku
Android Application ID: com.jackli717.sudoku
```

该标识不依赖实际域名所有权，并在两个平台保持一致。向 App Store Connect 或 Google Play 注册后不得更改；应用面向用户的显示名称仍为 `Hard Sudoku Pro`，与内部标识相互独立。

## 10. 已确认的决策摘要

- 使用 React Native 同时支持 iPhone 和 Android 手机。
- iOS 和 Android 的正式应用标识统一使用 `com.jackli717.sudoku`。
- 题库由专人在发行前提供。
- 题库只随 App 版本更新，不建设在线更新能力。
- 使用 SQLite 管理题库。
- 题库数据库与用户数据库分离。
- 本地题库保存题面和完整答案。
- 接受高级用户可能提取本地题库和答案这一现实，不在首期增加服务器或复杂加密。
- 首期支持英语、日语、德语和简体中文。
- 首期为不要求登录的单人离线游戏，不建设云同步、排行榜、对战、活动或社交系统。
- 已决定未来可通过 Firebase Analytics Spark 免费方案收集最小匿名留存和功能事件，但当前暂缓接入；分析失败或关闭时不得影响任何离线游戏能力。
- 发行前建设 Cloudflare 托管的最小静态官网，只提供首页、隐私政策、支持及必要条款，不建设网站后台、数据库或账号系统。
- 首期只允许一局未完成游戏；返回首页保存进度，开始新局前必须明确继续或放弃当前游戏。
- 自动检查开启时错误确定数字保留并标红，但不参与候选数清理、快速铅笔生成或智能提示分析。
- 达到三次错误后允许重新挑战同一道题或开始新局，失败尝试不发放奖励，已消耗额度不退还。
- 所有合法完成均可刷新最佳时间，不按智能提示或快速铅笔使用情况拆分纪录。
- 自动插屏只设置在用户明确开始或继续游戏后、棋盘显示前；游戏进行中不自动插入广告。
- 智能提示和快速铅笔使用本地额度，额度耗尽后可由用户主动观看激励广告补充。
- 首次完成题目根据 Level 1–5 奖励额度，完美完成和连续完成提供额外奖励。
- Premium 使用一次性非消耗型购买，移除自动广告并无限使用智能提示和快速铅笔。
- 语言资源与题库完全分离，缺失翻译时回退英语。
- 题库发行前必须经过自动化合法性、唯一解和重复性验证。
- 题目以 Level 1 至 Level 5 展示，等级主要由最低必需技巧等级决定。
- 同一级别内使用技巧次数和累计分数进行排序与校准。
- 猜测和回溯不属于面向用户的解题技巧；回溯只用于唯一解验证。
- 评级规则、技巧定义和检测顺序必须版本化并可复现。
- 首期逐步提示由运行时可解释逻辑求解器生成，而不是直接显示数据库答案。
- 提示采用“观察方向、推理结果、应用结果”三个阶段。
- HoDoKu2 仅作构建期生成、评级和对照工具；App 使用宽松许可证的运行时人类技巧引擎，两者共享技巧规范、优先级和 `HintStep` 契约而不强求共享代码。
- 手工草稿、可编辑的快速草稿、瞬时完整候选数与持久化的 `hintCandidates` 分开管理；玩家草稿不能反向影响提示推理。
- 提示结果使用结构化数据驱动高亮、多语言解释、动画和自动应用。
- 项目使用 `tools/puzzle-generator` 作为简单的离线题目生成辅助工具。
- 该工具使用固定版本的 HoDoKu2 生成题面、唯一答案和评级路径，并按项目规则输出 Level 1–5、审计报告和 SQLite 题库。
- 该工具不扩展为题库后台或完整运营系统，也不进入移动 App。
- 当前100道题是流程验证集；正式发行目标为 `10,000–30,000` 道验收合格题目，最终难度分布上线前确定。
