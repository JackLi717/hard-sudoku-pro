# Hard Sudoku Pro：首期产品与数据架构决策

## 1. 文档目的

本文档记录 Hard Sudoku Pro 首期已经确认的产品边界与技术方向，作为后续设计、开发、题库交付、测试和发行的共同依据。

当前阶段只确定项目基础架构、题库管理方式、答案存储策略和多语言要求，不在本文档中定义具体游戏界面、交互流程、计分规则或商业化内容。

## 2. 首期范围

### 2.1 目标平台

- Apple iPhone（iOS）。
- Android 手机。
- 使用 React Native 开发，当前项目版本为 React Native 0.87.1。

### 2.2 题库来源

- 题库内容由专人在 App 发行前提供。
- App 不提供在线题库管理后台。
- App 运行期间不从服务器下载、同步或热更新题库。
- 题库只能随着新版本 App 的发布而更新，以降低开发和长期维护成本。

### 2.3 首期非目标

- 不建设题库更新服务器或同步服务。
- 不支持运营人员在 App 发布后远程增加、删除或修改题目。
- 当前不设计具体游戏内容、页面和玩法细节。
- 当前不把本地成绩视为具有防作弊能力的竞技成绩。

## 3. 总体数据架构

题库数据和用户数据应使用两个相互独立的 SQLite 数据库。

| 数据库 | 主要内容 | 生命周期 |
| --- | --- | --- |
| `content.sqlite` | 题目、答案、难度、来源、题库版本等发行内容 | 随 App 版本发布，可被新版题库整体替换 |
| `user.sqlite` | 做题进度、完成记录、用时、设置和语言选择等用户数据 | App 升级时保留，并通过数据库 migration 演进 |

将两个数据库分开的主要原因：

- 更新题库时不会覆盖用户进度。
- 题库可以作为经过验收的只读发行物处理。
- 用户数据库可以独立备份、迁移和排查问题。
- 数据职责清晰，降低升级逻辑和后期维护难度。

应用代码应通过统一的数据访问层读取题库，不应让页面组件直接执行 SQL。

## 4. 题库数据库

### 4.1 建议的最小数据结构

以下结构仅表示首期需要保存的核心信息，最终 schema 可在正式开发时进一步确定：

```sql
CREATE TABLE puzzles (
  id TEXT PRIMARY KEY,
  puzzle TEXT NOT NULL,
  solution TEXT NOT NULL,
  difficulty_level INTEGER NOT NULL CHECK (difficulty_level BETWEEN 1 AND 5),
  difficulty_score INTEGER NOT NULL,
  hardest_technique TEXT NOT NULL,
  rating_version TEXT NOT NULL,
  source TEXT,
  content_version INTEGER NOT NULL,
  checksum TEXT NOT NULL,
  enabled INTEGER NOT NULL DEFAULT 1
);
```

字段原则：

- `id` 是题目的稳定标识，一经发行不应因排序或重新导入而改变。
- `puzzle` 使用固定 81 个字符表示题面，空格建议用 `0` 表示。
- `solution` 使用固定 81 个字符表示完整答案。
- `difficulty_level` 保存展示给用户的数字等级 `1` 至 `5`。
- `difficulty_score` 用于同一等级内的排序和难度校准，不直接展示给用户。
- `hardest_technique` 保存评级求解路径中必需的最高技巧代码。
- `rating_version` 标识产生当前评级的规则和求解器版本。
- `source` 用于记录题目来源或供应批次。
- `content_version` 标识题库内容版本。
- `checksum` 用于完整性和重复性检查，不作为安全加密手段。
- `enabled` 允许在不立即删除历史数据的情况下停止分配某道题。

如果未来需要题包、主题、作者或分类，可以新增独立表，不必在首期预先设计所有可能字段。

### 4.2 题库交付与生成

建议由内容提供者提交约定格式的 CSV、JSON 或 SQLite 文件，再通过构建脚本生成最终的 `content.sqlite`。不建议直接把未经自动验证的人工文件放入安装包。

推荐流程：

1. 内容人员按照固定的数据规范提交题目。
2. 构建脚本执行格式、合法性、唯一解和重复题检查。
3. 验证全部通过后生成最终 `content.sqlite`。
4. 将数据库作为 App 安装包资源发布。
5. App 首次启动时将其复制到应用私有数据目录并以只读方式使用。

#### HoDoKu2 离线生成决策

首期正式采用 HoDoKu2 `2.4.3 build 116` 作为离线候选题生成器、答案求解器和逻辑路径分析器。固定 JAR、配置、许可证与评级规则保存在 `tools/puzzle-generator/`，但不进入 React Native App 安装包。

HoDoKu2 的原始五级标签只负责产生不同难度的候选池。项目最终的 `difficulty_level` 由完整逻辑路径中最高的 HSP 技巧等级决定，HoDoKu2 累计分数保存为 `difficulty_score`，只用于同级排序。构建流程同时保存原始输出和版本校验值，保证结果可以审计。

### 4.3 发行前自动验证

每次生成题库至少应检查：

- 题面和答案都恰好包含 81 格。
- 字符只包含约定的数字和空位表示符。
- 题面中的已知数字与答案一致。
- 答案的每一行、每一列和每个九宫格都合法。
- 每道题有且只有一个解。
- 不存在重复题目。
- 每个 `id` 唯一且稳定。
- 题目可由项目支持的逻辑技巧完整解出，不需要猜测或回溯。
- 难度等级、分数、最高技巧和评级版本均有效。
- 题库 schema 版本和内容版本均有效。
- 最终数据库可在 iOS 和 Android 构建中正常打开和查询。

内容提供者可以提交预期等级和预期技巧，但正式等级必须由项目自己的统一评级器计算。提供方等级与系统等级不一致时，题目应进入人工复核，不能直接采用提供方标签。

### 4.4 基于解题技巧的难度体系

#### 4.4.1 评级原则

题目等级应由“完整解出题目所必需的最高技巧等级”决定，再使用技巧出现次数和总解题步骤计算工作量分数，用于校准同一等级内的相对难度。

不能只用题目给定数字的数量判断难度；也不能只统计最高技巧而忽略解题路径。一道只需要一次高级技巧的题，与一道需要大量中高级步骤的题，实际体验可能明显不同。

推荐公式为：

```text
最终等级 = 完整解题所需的最低技巧等级上限
同级排序 = 各技巧权重乘以使用次数后的累计分数
质量复核 = 自动评级 + 人工试玩抽检
```

#### 4.4.2 首版五级技巧建议

以下分组作为首版起点，正式权重和边界应根据题库样本与人工试玩结果校准：

| 显示等级 | 允许且可能必需的最高技巧 | 预期体验 |
| --- | --- | --- |
| 1 | 最后一格、唯一候选数、隐性唯一候选数 | 入门，可通过直接观察完成 |
| 2 | 宫区交互、指向数、区块排除、显性数对、隐性数对 | 基础逻辑 |
| 3 | 显性/隐性三数组、四数组、X-Wing | 中高级，通常需要完整候选数 |
| 4 | XY-Wing、XYZ-Wing、Swordfish、Skyscraper、Two-String Kite、简单染色 | 高级技巧 |
| 5 | Jellyfish、XY-Chain、AIC、复杂染色、强制链等 | 专家级 |

技巧难度具有一定主观性，不同求解体系对技巧顺序和名称可能有不同定义。部分技巧也可以用其他技巧体系表达。例如 Skyscraper 可以被视为 Turbot Fish 或 X-Chain。因此，项目必须固定自己的技巧代码、定义、所属等级和检测顺序，不能在同一评级版本内随意改变。

首期规则：

- 所有 Level 1 至 Level 5 题目都必须能用项目支持的逻辑技巧解出。
- 猜测、试错和通用回溯算法不属于 Level 5 技巧。
- 回溯算法只能用于验证唯一解，不能用于计算展示给用户的难度。
- 超出当前逻辑求解器支持范围的题目不能进入正式题库。
- Level 5 的技巧边界应在收到首批题目后复核，避免范围过宽或题量不足。

#### 4.4.3 自动评级流程

评级器应按固定顺序从简单技巧开始，并逐级启用技巧：

```text
验证题目格式和唯一解
        ↓
只启用 Level 1 技巧，尝试完整求解
        ↓ 未解出
启用 Level 1–2 技巧，从原题重新求解
        ↓ 未解出
依次增加 Level 3、Level 4、Level 5
        ↓
记录能够完整解题的最低等级
        ↓
记录完整求解轨迹、最高技巧、技巧次数和累计分数
```

求解器必须遵守以下确定性要求：

- 每一步始终优先检查较简单的技巧。
- 同一状态存在多个可用步骤时，使用固定的技巧顺序和格子顺序。
- 每次评级相同题目都应产生一致结果。
- 不能因为某一步可以使用更高级技巧，就人为提高本来可由低级技巧解出的题目等级。
- 应保存求解轨迹或轨迹摘要，保证评级结果可以审计和复现。

#### 4.4.4 技巧权重和工作量分数

每种技巧应配置：

- 稳定的 `technique_code`。
- 所属等级。
- 评级器中的检测顺序。
- 工作量权重。
- 多语言显示名称和说明所使用的翻译键。

题目分数可以采用以下基础模型：

```text
difficulty_score = Σ（技巧权重 × 使用次数）
```

最高技巧决定最低等级，累计分数可以把题目提升到更高等级，或用于同级排序，但具体阈值不应在缺少真实题库样本和试玩数据时过早固定。

为了保留每道题的评级依据，建议增加技巧使用明细表：

```sql
CREATE TABLE puzzle_technique_usage (
  puzzle_id TEXT NOT NULL,
  rating_version TEXT NOT NULL,
  technique_code TEXT NOT NULL,
  use_count INTEGER NOT NULL,
  PRIMARY KEY (puzzle_id, rating_version, technique_code)
);
```

如果需要保存完整解题轨迹，可在构建产物中保留独立的评级报告，而不必把所有步骤放入面向用户的运行时数据库。

#### 4.4.5 评级版本管理

技巧等级属于项目定义，并非永久不变的客观标准。每套规则必须使用独立版本，例如：

```text
rating_version = "hsp-1.0"
```

发生以下变化时必须提升评级版本，并重新评定全部题目：

- 增加、删除或重新定义技巧。
- 调整技巧所属等级。
- 调整技巧检测顺序。
- 修改技巧权重或等级分数阈值。
- 修复会改变解题路径或结果的求解器错误。

同一 App 版本内只能采用一套正式评级规则，避免相同题目在没有明确原因时显示不同等级。

#### 4.4.6 题库验收报告

构建流程应为每道题生成可供内容人员和测试人员检查的报告，例如：

```text
题目 ID：puzzle-00128
提供方等级：4
系统等级：4
最高技巧：XY-Wing
总逻辑步骤：63
技巧使用：
  Hidden Single × 24
  Locked Candidates × 8
  Naked Pair × 3
  XY-Wing × 1
唯一解：通过
评级版本：hsp-1.0
```

每个等级都应抽取足够题目进行人工试玩，重点检查系统评级与真实玩家感受是否一致，以及同一级别内是否存在明显的难度跳跃。

#### 4.4.7 用户展示与多语言

首期主要向用户显示跨语言一致的数字等级：

```text
Level 1
Level 2
Level 3
Level 4
Level 5
```

在题目详情、帮助或技巧教学中，可以额外显示该等级可能需要的技巧。技巧名称使用稳定代码和翻译键管理，例如：

```json
{
  "technique.xWing": "X-Wing",
  "technique.hiddenPair": "Hidden Pair"
}
```

英语、日语、德语和简体中文的技巧名称应由熟悉数独术语的人审核。部分高级技巧在不同地区缺少统一译名，必要时可保留英文名称作为副标题。

### 4.5 可解释的逐步提示引擎

#### 4.5.1 功能目标

提示功能不是直接显示答案，而是基于玩家当前棋盘状态，用人类能够理解的逻辑技巧逐步解释下一步。一次完整提示需要支持：

1. 高亮相关行、列、宫、格子和候选数，并指出所使用的技巧。
2. 标出可以排除的候选数或可以确定的数字，并解释推理原因。
3. 经用户确认后应用结果，并将操作加入撤销历史。

这一能力需要系统内置“可解释的人类逻辑求解器”。只读取 `content.sqlite` 中的完整答案，或者使用只返回最终答案的回溯求解器，无法产生可靠的技巧依据和逐步讲解。

#### 4.5.2 两类求解能力

系统应区分两个用途不同的模块：

| 模块 | 用途 | 是否直接用于用户提示 |
| --- | --- | --- |
| 精确求解器 | 唯一解验证、题库检查、检测无解状态 | 否 |
| 人类逻辑求解器 | 难度评级、寻找下一步技巧、生成提示和技巧教学 | 是 |

精确求解器可以在内部使用回溯算法；人类逻辑求解器只能使用项目正式定义的 Level 1 至 Level 5 技巧。数据库答案可以辅助识别错误输入或验证完成状态，但不能替代逻辑推理过程。

#### 4.5.3 构建时与运行时职责

题库构建时生成的标准解题路径可用于评级、验收和测试，但不能直接作为运行时的唯一提示来源。玩家可能采用不同顺序、已经完成部分标准步骤、只填写部分候选数，或者在中途输入错误数字。

推荐采用混合模式：

- 构建题库时生成标准求解轨迹和评级报告。
- App 运行时根据玩家当前棋盘重新寻找下一条可解释步骤。
- 构建时评级器和运行时提示引擎共享相同的技巧检测器、技巧代码、等级和顺序。
- 玩家在提示的任一阶段修改棋盘后，当前提示立即失效并重新计算。

#### 4.5.4 结构化提示结果

求解器不能直接生成中文、英文等自然语言文本，而应返回与语言和界面无关的结构化结果，例如：

```ts
type HintStep = {
  techniqueCode: 'lockedCandidates.pointing';
  difficultyLevel: 2;
  focusCells: CellRef[];
  focusRegions: RegionRef[];
  premiseCandidates: CandidateRef[];
  eliminations: CandidateRef[];
  placements: Placement[];
  explanationKey: 'hint.lockedCandidates.pointing';
  explanationParams: {
    digit: number;
    box: number;
    row: number;
  };
};
```

同一份 `HintStep` 应同时驱动：

- 棋盘区域、关键格子和候选数高亮。
- 排除数字或确定数字的动画。
- 三阶段提示内容。
- 英语、日语、德语和简体中文解释。
- 自动应用和撤销操作。
- 单元测试和提示结果快照测试。

例如“指向数”技巧不应只返回“删除候选数 7”，而应同时描述作为前提的宫、行、候选位置，以及所有可排除位置。

#### 4.5.5 三阶段提示交互

第一阶段为“观察方向”：

- 告诉用户当前建议使用的技巧。
- 高亮相关区域、关键格子和构成推理依据的候选数。
- 不显示最终需要排除或填写的结果。

第二阶段为“推理结果”：

- 使用另一种视觉状态标出可排除候选数或确定数字。
- 显示推理原因。
- 暂不自动修改棋盘。

第三阶段为“应用结果”：

- 删除对应候选数或填入确定数字。
- 播放简短且可关闭的反馈动画。
- 将变化加入撤销历史。
- 记录本题使用提示的次数和阶段。

三阶段必须来自同一个不可变的 `HintStep`。如果棋盘版本发生变化，旧提示不能继续应用。

#### 4.5.6 玩家候选数与系统候选数

系统应维护两个不同概念：

- `userCandidates`：玩家实际记录、删除或保留的候选数。
- `solverCandidates`：求解器根据当前已填数字计算的完整合法候选集合。

提示引擎不能假设玩家已经填写全部候选数，也不能仅依赖玩家笔记进行推理。玩家漏记或误删候选数时，系统仍应能够正确分析棋盘。因此逻辑求解器主要使用 `solverCandidates`，玩家候选数用于界面表现和交互，并在应用提示时按产品规则同步。

#### 4.5.7 提示前的状态检查

每次请求提示时应按以下顺序处理：

1. 检查行、列和宫内是否有重复数字。
2. 检查当前输入是否让题目变为无解。
3. 如果产品启用了错误检查，识别与标准答案冲突的用户输入。
4. 根据当前已填数字重新计算系统候选数。
5. 从最低等级技巧开始寻找可用逻辑步骤。
6. 返回第一个确定、有效且可解释的 `HintStep`。

如果当前棋盘已经无解或存在冲突，不应继续提供正常技巧提示，而应先引导用户检查冲突或撤销错误步骤。

#### 4.5.8 提示选择策略

提示引擎应与难度评级器使用相同的“简单技巧优先”策略：

- 优先返回当前可用的最低等级技巧。
- 同级技巧按照固定顺序选择。
- 同一棋盘状态应稳定返回同一个优先提示。
- 提示不得使用高于题目正式评级且并非必需的技巧来制造难度。

技巧检测器应返回推理依据和结果，而不是直接修改棋盘。界面只有在第三阶段并获得用户操作后才应用结果。

#### 4.5.9 共享核心架构

难度评级、提示、技巧教学和题库验收必须共用一套技巧检测核心：

```text
技巧检测器
   ├── 题库难度评级
   ├── 发行前解题报告
   ├── 运行时逐步提示
   ├── 技巧教学
   └── 自动化测试
```

如果评级器与提示系统分别实现，可能出现题目评级与实际提示技巧不一致、技巧定义重复或多语言说明不同步等问题。

#### 4.5.10 技术实现和测试

9×9 数独的数据规模很小，首期可以使用与 React Native UI 分离的纯 TypeScript 模块实现，无需为性能单独开发 iOS/Android 原生求解模块。

建议目录：

```text
src/
  sudoku/
    core/
      board.ts
      candidates.ts
      validation.ts
    solver/
      exactSolver.ts
      logicalSolver.ts
      techniques/
        singles.ts
        lockedCandidates.ts
        subsets.ts
        xWing.ts
        xyWing.ts
        chains.ts
    hints/
      hintEngine.ts
      hintTypes.ts
      hintSelection.ts
```

每种技巧至少需要覆盖以下自动化测试：

- 可以正确识别该技巧的棋盘状态。
- 相似但不满足条件时不会误识别。
- 高亮区域和推理依据完整且正确。
- 排除或填写结果正确。
- 应用结果后棋盘保持合法。
- 四种语言所需的解释参数齐全。
- 相同棋盘状态产生确定且可复现的提示。

提示引擎是难度评级、题库质量、技巧教学和实际游戏体验共用的核心能力，应作为独立领域模块开发，而不是作为页面组件中的临时逻辑。

## 5. 简单题目生成辅助工具

### 5.1 定位与范围

项目包含一个独立目录：

```text
tools/puzzle-generator/
```

该目录用于规划一个只为 Hard Sudoku Pro 准备发行题目的离线辅助工具。它不是完整的出题系统，不承担题库运营、内容审批、在线服务或发行管理职责，也不会被打包进 iOS/Android App。

当前阶段只建立目录和职责边界，不编写具体生成、求解或评级代码。实现语言、算法和数据格式需要在后续评审中确定。

### 5.2 核心目标

工具只负责三件事：

1. 生成合法的数独题面。
2. 生成并验证题目的唯一答案。
3. 按项目约定的技巧等级，将题目评价为 Level 1 至 Level 5。

最小工作流程为：

```text
生成完整终盘
  -> 移除部分数字形成题面
  -> 检查题目是否只有一个答案
  -> 评价解题所需技巧和难度
  -> 输出题面、答案和难度等级
```

### 5.3 计划输入与输出

计划输入：

- 需要生成的题目数量。
- 目标难度等级或等级分布。
- 用于复现生成结果的随机种子。
- 评级规则版本。

每道题计划只输出最基本的信息：

```text
id
puzzle
solution
difficultyLevel
difficultyScore（可选，只用于同级排序）
hardestTechnique
ratingVersion
```

输出格式可以在 JSON、CSV 或 SQLite 中选择，但当前阶段不做决定。生成结果以后再通过独立的简单步骤放入 App 使用的 `content.sqlite`。

### 5.4 目录框架

```text
tools/
  puzzle-generator/
    README.md
    generation/       # 题面和唯一答案生成职责
    difficulty/       # Level 1–5 难度评价职责
    output/           # 生成结果存放位置
```

当前各目录只有职责说明，没有可执行实现。

### 5.5 明确的非目标

- 不建设题库管理后台。
- 不支持在线题库更新或同步。
- 不设计供应商数据导入适配器。
- 不设计复杂的人工审批和运营流程。
- 不负责发行题量筛选和题库组合管理。
- 不实现复杂的结构等价题检测。
- 当前不实现 SQLite 导出器或综合报告系统。
- 当前不编写生成器、求解器或评级器代码。

### 5.6 与 App 提示功能的边界

题目生成辅助工具只输出题面、唯一答案和难度评价。App 中根据玩家当前棋盘进行区域高亮、候选数排除和逐步技巧讲解，属于独立的运行时提示功能。

两者未来可以共享技巧名称和难度规则，但当前不要求共用同一个代码包。是否共享具体实现，应在开始编码前另行评审，避免为了未来复用而过早增加工具复杂度。

## 6. App 更新时的题库处理

题库虽然不支持在线更新，但仍需要处理 App 升级带来的本地数据库替换。

建议流程：

1. 安装包中携带当前版本的 `content.sqlite` 和内容版本号。
2. App 启动时比较安装包题库与本地题库的版本。
3. 如果安装包版本更高，先完成文件校验，再原子替换本地 `content.sqlite`。
4. `user.sqlite` 始终保留，不随题库替换而删除。
5. 用户进度通过稳定的 puzzle `id` 与题目关联。

如果新版题库删除或停用某道题，建议保留对应历史记录，但不再将该题分配给用户。这样可以避免用户已经完成的统计突然消失。

## 7. 本地答案与安全性

### 7.1 已选择的方向

首期在 `content.sqlite` 中同时保存题面和完整答案。这是目前离线运行、降低开发与维护成本目标下最合适的方案。

这样做可以简化：

- 提示功能。
- 输入纠错。
- 完成状态校验。
- 自动化测试和题库验收。
- iOS 与 Android 的一致性实现。

### 7.2 可提取性的含义

具备一定技术能力的用户可能从 App 安装包或应用数据中提取题库和答案。主要影响包括：

- 用户可以绕过正常游戏过程查看答案。
- 完整题库可能被批量复制。
- 本地完成记录或本地排行榜可能被修改。
- 如果题库本身具有较高商业价值，可能涉及内容授权和知识产权风险。

即使数据库不保存答案，用户仍然可以提取题面并用公开的数独求解器计算答案。因此，只删除答案字段不能提供真正的保密能力。

SQLite 加密或代码混淆只能提高提取门槛。只要 App 必须离线读取数据，解密能力也必须存在于设备上，无法对熟悉逆向工程的用户实现绝对保密。

### 7.3 首期安全边界

- 数据库放在应用私有目录，不提供用户导出功能。
- 首期不为答案引入服务器或复杂加密方案。
- checksum 只用于校验完整性，不应被描述为加密或防篡改保证。
- 如果以后提供有奖金或实际价值的竞技排名，需要重新设计服务器端校验，不能信任本地成绩。
- 在签署题库授权协议时，应确认内容供应方是否允许题面和答案随离线 App 分发。

## 8. 多语言支持

### 8.1 首期语言

| 语言 | Locale |
| --- | --- |
| 英语 | `en` |
| 日语 | `ja` |
| 德语 | `de` |
| 简体中文 | `zh-Hans` |

本文档暂将“中文”定义为简体中文。繁体中文应作为独立语言 `zh-Hant` 处理，需要独立翻译和测试，不能简单视为简体中文的显示变体。

### 8.2 多语言架构

数独题目由数字组成，不需要为每种语言建立一份题库。语言资源必须与 `content.sqlite` 分离。

建议目录：

```text
src/
  localization/
    index.ts
    locales/
      en.json
      ja.json
      de.json
      zh-Hans.json
```

建议使用：

- `i18next` 和 `react-i18next` 管理翻译键、插值和回退。
- `react-native-localize` 检测设备首选语言并匹配受支持语言。

语言行为：

- 第一次启动时跟随设备首选语言。
- 如果设备语言不受支持，回退到英语。
- 设置中允许用户手动切换语言。
- 用户选择保存在 `user.sqlite`，优先级高于设备语言。
- 切换语言后立即生效，不要求重启 App。

### 8.3 文案管理原则

- 组件中不得硬编码用户可见文本。
- 数据库和业务代码只保存稳定代码，例如 `easy`，界面通过翻译键显示“Easy”“初級”“Einfach”或“简单”。
- 按钮、弹窗、错误消息、提示、帮助文本和无障碍标签都必须本地化。
- App 名称、权限说明等 iOS/Android 原生文案需要分别配置。
- App Store 和 Google Play 的商店介绍、截图文案属于独立的发行本地化内容。
- 翻译应由人工审核，尤其是候选数、提示、撤销和难度等数独术语。

### 8.4 界面设计约束

- 德语文案通常比英语更长，按钮和弹窗不能依赖过窄的固定宽度。
- 日语、中文和拉丁字符都需要进行真机字体和截断测试。
- 日期、时间和数字格式应遵循设备区域设置。
- 数独棋盘固定使用数字 `1` 至 `9`，不随界面语言转换为其他数字字符。

## 9. 当前技术方向

当前项目为 React Native 0.87.1。正式实现 SQLite 时，可优先评估 `react-native-nitro-sqlite`，原因包括：

- 支持现代 React Native 架构。
- 同时提供同步和异步查询接口。
- 支持 iOS 和 Android 应用数据目录。
- 较大查询和批量操作可放到异步路径，避免阻塞 UI。

正式引入依赖前仍需完成 iOS/Android 真机验证、维护状态检查和许可证确认。

## 10. 已确认的决策摘要

- 使用 React Native 同时支持 iPhone 和 Android 手机。
- 题库由专人在发行前提供。
- 题库只随 App 版本更新，不建设在线更新能力。
- 使用 SQLite 管理题库。
- 题库数据库与用户数据库分离。
- 本地题库保存题面和完整答案。
- 接受高级用户可能提取本地题库和答案这一现实，不在首期增加服务器或复杂加密。
- 首期支持英语、日语、德语和简体中文。
- 语言资源与题库完全分离，缺失翻译时回退英语。
- 题库发行前必须经过自动化合法性、唯一解和重复性验证。
- 题目以 Level 1 至 Level 5 展示，等级主要由最低必需技巧等级决定。
- 同一级别内使用技巧次数和累计分数进行排序与校准。
- 猜测和回溯不属于面向用户的解题技巧；回溯只用于唯一解验证。
- 评级规则、技巧定义和检测顺序必须版本化并可复现。
- 首期逐步提示由运行时可解释逻辑求解器生成，而不是直接显示数据库答案。
- 提示采用“观察方向、推理结果、应用结果”三个阶段。
- 提示引擎与难度评级器共享同一套技巧检测核心和确定性选择顺序。
- 玩家候选数与求解器候选数分开管理。
- 提示结果使用结构化数据驱动高亮、多语言解释、动画和自动应用。
- 项目保留 `tools/puzzle-generator` 作为简单的离线题目生成辅助目录。
- 该工具只规划生成题面、唯一答案和 Level 1–5 难度评价，不扩展为完整出题系统。
- 当前只建立该工具的目录和职责说明，不实现生成、求解或评级代码。
