# InviteSprout 引芽推荐服务产品与架构方案

更新日期：2026-10-06

状态：产品与架构建议稿，未启动公共 SaaS 实施、收费或云资源创建。

项目工作名：**InviteSprout**，中文名 **引芽**，代码标识 `invitesprout`。Invite 表示朋友邀请，Sprout 表示新芽与自然增长。此名称用于当前方案和后续工程标识；域名、商标和公开品牌定稿在正式发布前确认，当前没有购买域名。

本方案把 [数独推荐方案](referral-growth-system-plan.md) 中的邀请关系、条件判断、奖励凭证和统计抽成共用服务。Platon Sudoku 使用同一组 API，成为第一个项目；随后用一个真实的外部 App 验证通用性，再决定是否向开发者收取每月 5.99 或 7.99 美元。目标是分摊 AWS 成本并验证新的订阅业务，价格、客户数量与盈利都属于待验证假设。

## 1 产品定位与目标客户

建议定位：

> 帮助小团队快速接入、少维护一套好友推荐与奖励系统，同时支持已有用户账号和匿名参与身份。

首批客户是独立开发者和小团队，产品以休闲游戏、学习练习和简单工具为主。它们已经有能赠送的虚拟资源或体验权限，且至少有一批真实使用者，准备开展推荐实验。第一批优先 Android 与 React Native，避免同时维护所有平台 SDK。

“所有 App 都需要推荐”不是已成立的市场结论。刚上线且完全没有玩家的 App 可能暂时不愿支付固定月费；已经有成熟推荐系统的产品也未必需要我们。更有希望的客户是已经有少量活跃用户、想接入推荐、但不想开发维护这一模块的小团队。已有业务后台的客户可以通过服务端 API 提供可信事件，购买的价值是节省开发维护时间；没有业务后台的客户则使用服务提供的匿名参与能力。

客户购买的是开发维护时间、可靠的奖励处理和低集成成本。后端服务不能保证玩家愿意分享，也不能替客户设计全部玩法。宣传应描述可用能力，不承诺病毒式增长或一定带来下载。

## 2 同类服务与差异假设

2026-10-06 核对的官方公开页面显示，推荐后台、移动 SDK 和奖励处理已有竞争者。公开功能与价格说明不等于独立验收过它们的实际效果。

| 服务 | 官方公开信息 | 对本方案的启示 |
| --- | --- | --- |
| [GrowthRail](https://www.growthrail.dev/pricing) | Developer 免费计划每月 50 个成功推荐，提供 React Native 等 SDK 和 API | 低流量客户已有免费选择，价格低本身不是足够差异 |
| [Invitebase](https://www.invitebase.com/pricing) | 免费计划包含每月 100 个推荐，公开提供移动 SDK 与应用内奖励 | 不能把“移动推荐加虚拟奖励”宣传为无人提供的新类别 |
| [Cello](https://cello.so/pricing/) | 官方要求产品有可登录、可认证的 Web 或移动体验 | 无须开发者自建用户账号的轻量模式值得验证；不能据此推断全部竞品都不支持 |

建议验证三个差异：接入和维护成本低；同时适配已有账号及无账号、离线为主的 App；按低额固定费用提供明确额度和规则，不要求先接支付系统或现金返佣。匿名接入是能力之一，客户定位不限制为完全没有后台的产品。

匿名参加服务仍会产生可关联身份，不能宣传成完全没有身份或数据收集。它不需要客户自己做账号页面，但服务必须完成认证、隔离和奖励凭证管理。

## 3 共用服务与各 App 的职责

| 共用服务负责 | 接入 App 负责 |
| --- | --- |
| 项目和参与身份登记 | 分享入口、奖励说明和产品体验 |
| 邀请码、链接与邀请归因 | 原题、关卡或体验内容 |
| 条件和时间窗口判断 | 报告必要使用事件 |
| 奖励凭证生成与去重 | 将凭证转换为提示、金币或其他权益 |
| 发放状态、确认和失败重试 | 本地钱包或业务权益的原子保存 |
| 名额、配额和异常控制 | 自身免费、付费及退款政策 |
| 推荐漏斗与基本留存统计 | 判断玩法是否适合产品 |

平台不持有跨 App 的统一金币或用户钱包。奖励资源是由项目配置的代码，例如数独使用 `hint_credit`、另一游戏使用 `energy`、学习工具使用 `practice_credit`。服务理解资源代码、数量、接收人和条件，不知道每一种资源具体怎样消费。

数独的题面指纹、完成三题补给、七日日期条、提示推理和复盘留在数独模块。共同挑战的内容也由 App 实现，公共服务仅提供可以复用的邀请关系与事件条件。

首版只支持小额应用内虚拟奖励。现金、礼品卡、跨 App 积分、用户钱包托管和高价值购买权益解锁均另行设计，不用低价套餐默默承担这些责任。

## 4 最小通用流程

```text
Platon Sudoku ─────┐
其他 Android App ──┼─ 同一 API → AWS 推荐服务 → PostgreSQL
学习练习 App ──────┘                 │
                                    └─ 项目隔离、规则、奖励凭证、统计

每个 App 拉取自己的奖励凭证，在自身钱包或权益表中入账。
```

一次完整接入包含：登记参与身份，创建邀请，接受邀请，提交合格行为，领取凭证和确认入账。SDK 把重试、队列和凭证核验包装好，App 仍需编写分享入口和一个奖励兑现回调。

接口应包含这些通用能力：`registerParticipant`、`createInvitation`、`acceptInvitation`、`recordEvent`、`listRewardGrants`、`acknowledgeGrant`。这些名称描述功能，不是已经实现或冻结的公开 API。

同一个 `grant_id` 的客户端回调可能多次触发，业务方必须持久化去重。服务承诺服务器事务和正常重试内不新增相同业务奖励，不能声称网络和设备清数据条件下端到端绝对只调用一次。

平台可以提供两种兑现接法：没有后台的 App 通过客户端拉取签名凭证；已有后台的客户通过服务器 webhook 接收，再在其后台兑现。一个项目为一种资源选定权威兑现路径，不能让拉取和 webhook 各自发一份奖励。Webhook 需要签名、重试、幂等和失败日志。

## 5 规则模板与可信度

第一版采用有限模板，不建设任意脚本或拖拽规则编辑器：

1. 接受邀请后，朋友完成一次指定事件，双方领取奖励。
2. 首次事件满足后，至少经过指定时间，再完成另一个指定事件，双方领取追加奖励。
3. 邀请人累计完成若干个合格关系，获得一次纪念权益。

配置字段包含事件代码、次数、时间间隔、接受窗口、领取资格、双方资源与数量、邀请人每月名额。每次接受邀请保存当时承诺，未来规则修改只影响后来的邀请。服务收费和用户奖励规则分开记录。

事件可信度必须显式标记。客户端上报属于 `client_observed`，客户后台认证的事实属于 `server_verified`；仅凭字段里写了来源不能升级可信度，平台从实际鉴权渠道确定来源。匿名客户端不能冒充客户后台。

Android 无后台模式结合安装密钥、去重、活动挑战和 [Play Integrity](https://developer.android.com/google/play/integrity/overview) 控制风险。设备验证不能证明独立自然人或真实手工游戏，适合接受一定损耗的小额虚拟奖励。订阅购买、现金回报或需要强真实性的活动必须使用可信服务端事实和专门验证。

自动化安装归因首版支持 Google Play 的 [Install Referrer](https://developer.android.com/google/play/installreferrer)，邀请短码保留兜底。不要因为 API 通用就宣传已经全面支持 iOS；首次安装后的 iOS 自动恢复需要单独方案与验证，不通过设备指纹偷偷补齐。

## 6 多项目隔离与 AWS 架构

沿用一套 AWS 后端和 PostgreSQL，不为每个客户开一台机器。开发者组织是租户，一个组织可以有多个 App 项目；首个项目属于我们自己。

第一阶段建议只新增组织、项目和项目认证结构，将邀请、参与身份、事件、名额、凭证、统计全部归属到项目。用户标识只在项目内有效，不按邮箱、设备或广告 ID 跨客户拼接用户。

所有业务表携带 `tenant_id` 和 `app_id`。唯一约束及外键包含项目范围，例如 `(app_id, participant_id)` 和 `(app_id, event_id)`，相同外部用户 ID 可以出现在不同 App，仍是互不相干的身份。

项目上下文由认证凭证解析，不能只相信客户端传来的 `app_id`。App 包内可放公开项目 ID，不能放开发者管理密钥或服务端秘密。项目 ID 不授予读取参与者列表、改活动或发任意奖励的权限。

数据库建议用应用层项目范围约束和 [PostgreSQL 行级安全](https://www.postgresql.org/docs/current/ddl-rowsecurity.html) 双重隔离。运行角色不得具有绕过策略的权限，连接池在每个事务中设置和清理经过鉴权的项目上下文。后台任务、报表、缓存键、导出及 webhook 也必须按项目隔离；仅在表上增加一列并不等于完成多租户安全。

每项目限频、事件体积上限、队列并发上限和月额度保护其他客户。一个客户的爆量、脚本攻击或异常重试不能耗尽整台服务。保留管理员操作记录及项目密钥轮换，生产数据不出现在公开 SDK 日志。

AWS 起步预算沿用数独方案的每月 50–80 美元。增加客户后容量、日志、存储、备份和客服会增长；原预算只是早期共享部署假设，不是任意数量客户的永久成本。

## 7 产品接入与最小控制台

没有自己的推荐后台，不等于完全不用做 App 接入。客户仍要配置应用链接、接受邀请、报告行为和保存奖励。销售前必须用外部开发者验证这些步骤是否足够简单。

优先提供 HTTP API、一个 React Native 适配层和 Android 安装归因桥接示例，配套可运行的示例工程。接着根据真实客户选择补原生 Android 或 Flutter，暂不同时开发全套 SDK。

数独通过公共 API 使用服务，不直接查公共服务数据库，也不调用仅数独拥有的资格接口。第二个示例项目使用不同事件和奖励资源；真实外部 App 接入时，应以配置和适配代码完成，不给公共核心加另一批应用名称条件分支。

自用阶段可以用受保护的内部报表和配置 API，早期外部试用可以人工开通。面向付费自助客户后需要一个小型 Web 控制台，至少包含项目配置、安装说明与测试、活动规则与效果、订阅取消和数据导出。不能长期假设每个低价客户都由我们手工部署和排错。

收费前还需明确服务条款、数据处理职责、删除和保留政策、停服及导出安排。开发者付费使用 SaaS 的账单与各 App 玩家购买是不同业务，不接管客户的应用内购买账单。

## 8 收费建议与额度

建议首先验证每项目 7.99 美元/月的正常价，用 5.99 美元作为少量早期客户的同额度试验价。初期不设计两个差异模糊的正式套餐，不承诺未验证的永久优惠。

开发测试环境免费，生产可有明确期限的试用。完全没有流量的人可能不愿意长期付费，应允许停止活动和取消订阅；不能把长期闲置用户忘记退订作为商业模型。

建议试验套餐每月覆盖：一个生产 App、一个测试环境、2,000 个推荐服务月活参与身份、20,000 条去重后事件、100 个首次合格推荐关系和基本报表。数字是用于测量资源成本的起点，不是已经压测过的承诺。

“参与身份”只计本月使用推荐服务的安装或账号，不等于客户整个 App 的 MAU。邀请和事件必须有大小与频率上限；即使成功推荐很少，机器人流量也可能产生资源成本，所以不能仅按成功推荐数提供无限使用。

后台分别测量 API 请求、去重事件、活跃参与身份和合格关系，不把重复重试当成新成功推荐收费。推荐首次合格和追加留存节点是一份关系的不同节点，不能算成两名新用户。

默认不自动超额扣款。临近额度告警，达到限制后依据提前展示的规则限制新活动或新邀请；已经接受邀请的承诺仍可完成，已签发凭证仍能领取。为这部分履约预留有上限的额外容量，不能在玩家已经完成时因为开发者套餐耗尽突然取消奖励。

停订时关闭新活动并给予建议 30 天的已接受活动履约与导出窗口，这个义务计入容量和成本。实际期限在收费前固定并写明；逾期凭证和客户 App 的既有权益由明确停服政策处理，不通过一夜删除数据库解决。

## 9 收入与成本测算

以下假设收款、退款和其他可变费用预留为收入的 15%，不是支付服务商的实际费率。计算只看覆盖共享基础设施，不含人工、税、坏账、安全维护和增长后的扩容；收款渠道确定后替换为真实费用模型。

| 每月价格 | 预留 15% 后每客户收入 | 覆盖 50 美元需客户数 | 覆盖 80 美元需客户数 |
| --- | --- | --- | --- |
| 5.99 美元 | 约 5.09 美元 | 10 | 16 |
| 7.99 美元 | 约 6.79 美元 | 8 | 12 |

这些客户数只说明有机会分摊机器费，不意味着业务盈利。50 个 7.99 美元客户的月收入是 399.50 美元，预留 15% 后约 339.58 美元；还必须扣除当时的基础设施和维护工时，不能继续假设服务规模变大后只花 50 美元。

最敏感的成本可能是支持而不是数据库。假设一个 7.99 美元客户需要 20 分钟人工支持，内部工时按 30 美元/小时估算，当月支持成本就是 10 美元。这是假设示例，说明低价产品必须依靠清楚文档、模板、错误提示和测试工具，不能包含不限量代接入。

服务与数独分别记账：外部客户收入是否覆盖共用基础设施，以及服务自身是否覆盖增量开发、维护和支持，是两个不同结论。我们自用项目也记录真实用量，不凭空把它当成付费客户。

## 10 分阶段验证与交付

| 阶段 | 实施范围 | 判断标准 |
| --- | --- | --- |
| 自用可复用核心 | 项目隔离、有限规则、邀请、事件、凭证、API；数独作为首项目 | 完整推荐闭环通过，核心不依赖数独题库和钱包结构 |
| 通用性验证 | 不同资源的示例项目，再接一款真实外部 App | 不改公共业务逻辑即可接入，隔离和失败重试通过 |
| 人工开通的早期试用 | 邀请少量独立开发者，量接入时间与维护成本 | 真正上线使用，开发者愿意付费而非仅表达兴趣 |
| 最小商业化 | 小控制台、订阅、取消、额度、导出和删除 | 收费与停订可履约，支持成本可接受 |
| 扩展平台 | 根据客户需求添加 SDK、更多模板和容量 | 已有客户续用，新增能力有明确需求 |

建议先与 5–10 位目标开发者沟通需求，争取 3 款真实外部 App 接入、其中至少 2 款实际付费并续用，作为是否继续投入的早期证据。这是小规模产品判断，不是统计显著，也不授权在本轮联系任何人。

开发者访谈要问最近一次是否想做推荐、当时为什么没做、愿意给哪种奖励、是否接受匿名身份和哪些集成步骤。不要只问“一个便宜的推荐服务好不好”，那不能证明购买意愿。

验收包括两个租户使用同样 participant ID 和 event ID 互不干扰、读取及管理越权被拒绝、连接池上下文不串租户、定时任务与报表隔离、并发限额、重复 webhook 或拉取不双发、单客户流量异常不影响其他项目、停订后已承诺凭证可处理、导出和删除范围正确。

对外公开接口在真实第三方集成后就形成兼容承诺，即使数独仍处于首次发布前，也不能用重建数独开发数据的规则来破坏外部客户的身份、凭证或接口。收费前冻结初始外部协议边界，后续公开协议变更遵守明确兼容规则。

## 11 对当前项目的实施建议

建议从第一天将后台模型按项目隔离，建立明确 API 和资源代码，数独只保留自己的前端、游戏事实及奖励兑现适配。暂不搭完整公共 SaaS 商店或多平台 SDK，也不创建新的 Git 历史或独立仓库。

已有数独奖励数值、玩法和页面范围仍是待确认建议。用户本次提出通用服务方向，并不意味着批准所有数独奖励参数、外部客户收费、现金奖励或额外平台集成。

若确定沿这条路线实施，下一项明确交付应是“可复用推荐核心与数独首个接入”，包括项目隔离及第二项目测试；商业化模块在外部接入证明需求之后实施。这样自用投入可成为服务基础，新增产品投入也有清楚的阶段边界。

## 12 推荐技术栈与 AI 实施方式

用户负责提出产品想法，整体工程交由 AI 完成。技术选型优先文档完整、行为可验证、依赖数量可控和与现有数独衔接方便。选择建议如下；没有安装依赖或修改运行代码，实施时锁定经过集成测试的稳定补丁版本。

| 部分 | 推荐选择 | 目的 |
| --- | --- | --- |
| 语言和运行时 | TypeScript，Node.js 24 LTS | 与 React Native 客户端共用语言和接口类型，利用编译检查减少协议错误 |
| API 后端 | Fastify 5 | 以模块组织 REST API、校验、认证和日志，保持部署简单 |
| 数据库 | PostgreSQL 16 | 事务、唯一约束和行级安全处理推荐、名额及奖励一致性；匹配 Lightsail 可用版本 |
| 数据访问 | Drizzle ORM 与 node-postgres | 类型安全的普通查询，关键锁、约束和行级安全使用明确 SQL |
| 接口契约 | JSON Schema、TypeBox、OpenAPI | 同一份受控 schema 驱动输入校验、接口文档和 SDK 类型，避免重复定义 |
| 开发者登录 | Better Auth | 使用已有认证库实现控制台账号、会话和恢复流程，业务项目权限单独检查 |
| 后台任务 | PostgreSQL 任务队列，优先 pg-boss | 处理 webhook 重试、汇总及清理，复用现有数据库 |
| 小型控制台 | React、TypeScript、Vite | 静态构建，使用后端 API 完成登录、配置和报表 |
| App 适配 | REST API，加 TypeScript SDK 和 Android 原生归因桥接 | 先服务当前 React Native 数独，再按客户需求扩展 |
| 部署 | Docker Compose、Caddy、AWS Lightsail | 可重复部署后端、任务进程和 HTTPS；生产数据库独立托管 |
| 检查 | TypeScript、Vitest、真实 PostgreSQL 集成测试、Playwright | 核验类型、并发事务、隔离以及控制台关键流程 |
| 订阅 | 商业化阶段接 Stripe Billing | 开发者订阅与玩家奖励分开，使用签名 webhook 同步套餐状态 |

Node.js 24 当前属于 LTS，适合作为新服务运行时；现有数独的 Node 配置不因此被修改。[Node.js 发布状态](https://nodejs.org/en/about/previous-releases)

Fastify 5 有公开支持政策和 schema 校验接口；当前支持表可能未穷举新 Node 版本，实施时在 Node 24 对具体插件组合做集成检查，而不是仅凭推荐表声称兼容已验收。[Fastify 支持政策](https://fastify.dev/docs/latest/Reference/LTS/)、[校验与序列化](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/)

PostgreSQL 16 仍受社区支持，Lightsail 官方列有该引擎；部署时使用该主版本最新可用稳定小版本。[PostgreSQL 支持政策](https://www.postgresql.org/support/versioning/)、[Lightsail 引擎](https://docs.aws.amazon.com/lightsail/latest/userguide/amazon-lightsail-choosing-a-database.html)

Drizzle 支持 PostgreSQL 及事务，生成的结构变更需要检查关键约束和安全策略，不能只依靠 ORM 自动猜出多项目隔离。[PostgreSQL 接入](https://orm.drizzle.team/docs/get-started/postgresql-new)、[事务](https://orm.drizzle.team/docs/transactions)

Better Auth 官方提供 Fastify 与 Drizzle 适配。它用于开发者控制台的账号认证，不自动验证玩家事件，也不能代替项目级授权或数据库隔离。[Fastify 适配](https://better-auth.com/docs/integrations/fastify)、[Drizzle 适配](https://better-auth.com/docs/adapters/drizzle)

任务队列、控制台和测试选型分别依据 [pg-boss](https://github.com/timgit/pg-boss)、[Vite](https://vite.dev/guide/)、[Vitest](https://vitest.dev/guide/) 和 [Playwright](https://playwright.dev/docs/intro) 的官方资料。订阅阶段采用 [Stripe Billing](https://docs.stripe.com/billing/subscriptions/overview)，实际收款费用与账号条件届时核实，不将此前 15% 测算预留称为 Stripe 的费率。

### 单体模块与工程边界

后端采用一个代码库、一个 PostgreSQL 和模块化单体。API 与任务进程使用同一份领域逻辑，部署时可以分开运行，方便限制任务并发。模块包括开发者身份、项目、参与者、邀请、规则、奖励、报表，计费在商业化阶段加入。

建议服务最终工程包含 `apps/api`、`apps/worker`、`apps/console`、`packages/contracts`、`packages/sdk`、`infra` 与 `docs`。这是服务自身的建议结构，不移动现有数独目录，也不在本轮创建另一个仓库。实际代码落点在实施范围明确后确定。

API 和 SDK 的共享范围限于协议与校验定义，不把数据库模型、服务器秘密、租户管理逻辑或钱包实现打包进 SDK。控制台静态资源可以由同一 HTTPS 入口提供，降低跨域会话配置复杂度；公开邀请页由后端输出受控 HTML，以便生成 App 专属分享预览，内容必须转义。

关键业务使用 PostgreSQL 事务、唯一约束和必要行锁。奖励创建和待投递记录同事务提交，再由任务进程投递；任务可能重试，业务端仍按凭证 ID 去重。任务库的内部 schema 与项目业务表分开，任务按项目上下文处理，任务运行身份不能成为绕过租户检查的通道。

开发环境用 Docker Compose 启动 API、任务进程和 PostgreSQL。生产 Compose 连接 AWS 托管 PostgreSQL，不再起第二个生产数据库容器。选择 [Caddy](https://caddyserver.com/docs/automatic-https) 处理入口和证书，Cloudflare 沿用现有 DNS；开启代理时同样保留安全的源站 HTTPS 和正确可信代理配置。

第一阶段不增加微服务、Kubernetes、Redis、Kafka 或多区域数据库。出现明确容量瓶颈后再选择需要的组件，避免让低价服务承担尚未需要的基础设施费用。

### AI 负责的工程交付

AI 负责把产品规则转换为数据模型和 API，完成后端、SDK、控制台、数独适配、必要测试、部署配置和运维说明。日常技术与框架选择由 AI 根据已定边界处理，不要求用户逐个选择库。

验收必须产生可检查的结果：两个项目数据隔离；重复事件与并发请求不重复发奖；没有后台的 App 能跑通推荐；已有后台模式能确认事件；网络或后台失败后能恢复；云端备份可恢复；实际费用在预算假设内。用真实 PostgreSQL 验证这些行为，不能只用模拟数据库的单元测试代替。

自动检查包括锁定依赖后的可重复安装、类型检查、关键领域测试、真实数据库集成测试、OpenAPI 与 SDK 契约检查和关键浏览器流程。后端测试与原数独 Jest 分开运行，只在数独接入时运行相关 App 回归，不为新服务改动原 App 测试配置。

用户提供产品取舍、预算和必要的云账号授权，正式收费及对外条款由用户决定。生产部署使用准备好的配置和限定权限，不把密钥粘贴到代码或日志。AI 可以完成工程，但“已写完代码”不能被当成已通过部署、隔离、备份或商店验收。

依赖小版本、Docker 镜像和客户端插件在实施时固定并验证；不使用浮动 `latest` 作为生产部署依据。首次真实第三方集成后，公开 API、SDK 和奖励凭证按明确兼容承诺演进。
