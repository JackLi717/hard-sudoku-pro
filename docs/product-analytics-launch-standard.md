# Platon Sudoku 产品分析设计与上线前标准

更新日期：2026-10-08

状态：产品负责人已确认将免费产品分析能力纳入上线前标准。Android 已接入 Analytics、Crashlytics/NDK 与 JS 诊断；已创建隔离的正式、测试 Spark 项目并登记维度、指标及六组报告。测试事件已到达 DebugView。实现、入口和限制见[接入与操作文档](operations/product-analytics-runbook.md)。完整上线验收尚未通过；复选框只有在对应检查实际通过后才能勾选。

核心游戏继续离线运行，通过商店、Firebase Analytics、AdMob 和故障监控观察获客、激活、留存、游戏体验与经营表现。优先实现无需新增服务费用的能力，不建设自有后台，不绑定 Firebase 账单账户，不为了复杂分析启用付费服务。

本文作为产品分析范围、统计口径和发布验收的当前依据，取代此前文档中“产品分析暂缓接入”的决定。奖励数量、商业权益和玩法仍以现有产品文档为准，不因分析需求改变。

## 目标与实施边界

分析必须回答以下问题：

1. 用户从哪里来，商店页面能否吸引安装。
2. 新用户是否顺利开始游戏，是否形成持续游玩习惯。
3. 难度、提示、快速候选、复盘和教学是否被使用，哪里存在阻碍。
4. 免费补给、自愿广告和永久购买是否支持产品持续经营。
5. 哪个版本、设备或流程出现崩溃、存档、提示或商业履约问题。

当前运营首发目标是 Google Play Android。Android 公开发行前完成适用的全部必做项；iOS 在自身公开发行前完成同等验收，不为等待 iOS 延迟 Android。课程与练习按最终公开构建的实际开放范围启用分析，不借此决定课程发行范围；预发布开放不得视为正式 Premium 权益。

本次文档交付不安装依赖、不修改应用、原生项目或数据库，不配置外部账号、不上传或发布构建。后续实施以本文为边界逐项完成。

## 免费能力与交付等级

“免费”指不新增分析服务费用，不代表没有开发、配置、隐私处理和日常检查工作。以官方实际可用能力为准；免费额度不等于可以无条件使用所有 Google Cloud 服务。

| 等级     | 含义                                                         | 上线要求                                                           |
| -------- | ------------------------------------------------------------ | ------------------------------------------------------------------ |
| 必做     | 可通过免费服务、已有平台和少量本地汇总完成的核心能力         | 公开发行前接入并验证，不因暂时没有真实用户而省略                   |
| 尽量完成 | 免费但需要更多关联、汇总或专门性能适配的分析                 | 上线前实际评估并优先实现；未完成须写清原因、免费替代结果及后续动作 |
| 暂不建设 | 自建后台、账单账户、付费分析、数据仓库及跨设备身份等范围扩展 | 不作为本次上线条件，也不为实现指标擅自启用                         |

免费能力默认尽量在上线前实现，不能仅以“高级分析”或“以后再看”为由推迟。必做项的验收对象是采集、口径、报表和故障处理能力，不要求上线前已经形成真实 D30 留存或达到某个营业收入。

| 能力                                     | 首期选择                                         | 等级与边界                                                            |
| ---------------------------------------- | ------------------------------------------------ | --------------------------------------------------------------------- |
| 商店获客、评价、使用和销售报表           | Play Console；iOS 发布时使用 App Store Connect   | 必做，保留各平台原始口径                                              |
| 应用行为、流程和留存                     | Google Analytics for Firebase，Spark，无账单账户 | 必做，使用免费标准报表与探索                                          |
| 广告收益与投放质量                       | 现有 AdMob 报表                                  | 必做，不增加广告网络或广告形式                                        |
| 崩溃与非致命错误                         | Firebase Crashlytics，与平台诊断互补             | 必做，验证 React Native、原生与 C++ 实际覆盖                          |
| 耗时与性能分布                           | 本地计时和分桶汇总                               | 必做关键耗时；更深入诊断尽量完成                                      |
| 更深入性能监控                           | Firebase Performance Monitoring                  | 尽量完成；先验证 RN 0.87 适配和额外采集范围，现有计时足够时可不加 SDK |
| 六张常用看板、异常通知                   | 各平台现有控制台、保存的报表及免费原生通知       | 必做；不承诺自动整合为一个实时控制台                                  |
| 任意跨局关联、逐题分析、长期完整离线历史 | 数据仓库或额外基础设施                           | 暂不建设，使用下述免费替代口径                                        |

Analytics、Crashlytics、Performance Monitoring 当前在 Firebase 定价页列为免费产品。保持 Spark，不启用 Blaze、BigQuery 导出、Cloud Functions、Firestore、Remote Config 或其他本次不需要的服务。[Firebase 定价](https://firebase.google.com/pricing)

即使某项服务提供免费额度，也不能据此扩展到账号、推荐归因、推送、远程实验或云钱包。

## 主指标与共同统计口径

### 主指标

主指标为每周有效游玩用户数，即过去七个 UTC 日期内至少发生一次有效游玩的可观测安装实例数。

有效游玩初始定义为：当天同一局游戏累计前台、未暂停的游玩时间达到 60 秒，且当天至少有一次玩家填写或笔记操作。排除广告、后台、暂停、复盘、课程、纯自动收尾和提示自动应用的时间或操作。达到条件后按安装实例、UTC 日期和游戏局在本地去重；多局或多日仍只按用户去重计入对应周指标。

这个指标衡量真正参与游戏，不能证明注意力持续在线，也不改变本地成绩或游戏计时规则。完成用户数作为配套指标，避免只增长游玩时长而没有完成体验。

### 单位与时间

| 项目         | 统一口径                                                    |
| ------------ | ----------------------------------------------------------- |
| 用户         | SDK 去标识化安装实例；不等于自然人，不跨平台合并            |
| 访问会话     | 使用 SDK 会话；与一局数独区分                               |
| 游戏局       | 从建立到完成、失败或明确放弃的同一局，允许跨访问和跨日继续  |
| DAU          | UTC 当天打开应用的可观测实例数                              |
| WAU 与 MAU   | 滚动 7 日和 30 日实例数；Play 的滚动 28 日 MAU 单独命名     |
| 游戏活跃     | 达到上述有效游玩条件                                        |
| 分析日期     | GA4 属性采用 UTC；设备时钟异常单列，不人工改写 SDK 事件时间 |
| 每日奖励日期 | 继续按现有手机本地日期，不改成 UTC                          |
| 时间与次数   | 同时报告总量、用户数与分布；局数、点击数不得代替用户数      |
| 零分母       | 显示无适用样本，不显示 0% 或 100%                           |
| 已成熟用户组 | 观察期已完整结束的首次打开日期分组                          |

首次打开优先使用 SDK 的 `first_open`，不手动重复发送。它表示安装或重装后首次启动，不是下载。[自动采集事件](https://support.google.com/analytics/answer/9234069?hl=en)

仅对正常可观测的首次打开计算新用户激活和安装留存。已有本地用户后续开启分析、首次采集迟于首次使用、标识重置等情况分别标记为既有用户或观测起点未知；不能伪装为全新安装。无法可靠判断时不进入严格新增用户分母。

默认使用设备口径、关闭 Google Signals 和不需要的广告个性化功能。不要自建另一套永久身份或设置跨设备 User ID。动态权益采用事件发生时的类别，避免用当前用户属性重写历史免费或付费状态。

## 获客与商店表现

以下必做指标直接使用商店现有报表。平台不提供的字段标注不适用，不以应用埋点猜测。

| 指标                       | 来源与用途                                 |
| -------------------------- | ------------------------------------------ |
| 商店曝光、详情页访问       | 商店报表，判断流量                         |
| 商店访问到安装转化         | 同一平台同一报表口径，判断素材与介绍       |
| 新增安装、首次打开         | 分开查看下载与真实启动，不相减推断精确流失 |
| 搜索、浏览、外部来源       | 商店已有来源分类，不建设用户级归因         |
| 国家、语言、设备和版本分布 | 平台支持的汇总维度，决定适配和市场投入     |
| 卸载与用户流失趋势         | 平台汇总，不能识别某个卸载用户             |
| 评分、评价量、主要问题     | 商店报表与人工阅读，每周归纳问题主题       |
| 买家、销售、退款、净收入   | 商店财务报表，作为经营事实来源             |

Play Console 已提供活跃和多种留存指标，包括滚动 28 日 MAU 和第 28 日留存。这些数据不能直接改名为 30 日 MAU 或 D30。[Play 统计口径](https://support.google.com/googleplay/android-developer/answer/139628?hl=en)

未来付费投放的获客成本、回收周期与推荐安装归因不属于本次接入范围。

## 新用户激活与留存

### 新用户流程

必做流程为“首次打开 → 首页可操作 → 第一局建立 → 首次玩家操作 → 有效游玩”，以及“第一局建立 → 首次完成 → 再次开局”。

| 指标                     | 分子与分母或计算方法                                   | 等级                           |
| ------------------------ | ------------------------------------------------------ | ------------------------------ |
| 首日开局率               | D0 开始游戏的新增实例 / 正常可观测新增实例             | 必做                           |
| 首日有效游玩率           | D0 达到有效游玩的新增实例 / 正常可观测新增实例         | 必做                           |
| 首次操作等待             | 同次前台流程内首页可操作到首次玩家操作的耗时分桶       | 必做                           |
| 首日完成率               | D0 完成至少一局的新增实例 / 正常可观测新增实例         | 必做                           |
| 首七日完成率             | D0 至 D6 完成至少一局的实例 / 已经过完整七日的新增实例 | 必做，配置用户流程或用户组探索 |
| 首局难度、求助、主动放弃 | 仅第一局，分别按用户或局明确标注                       | 必做                           |
| 完成后再开局             | 同次访问中完成后再次开局人数 / 有完成的访问用户数      | 必做，顺序流程探索             |
| 首次完成用时及跨日情况   | 游戏有效时长和日历跨度分别分桶                         | 必做                           |

首局耗时遇到离开流程、暂停或重新访问时分开处理，不把后台时间算为用户犹豫。首次完成按难度分组，困难局不与入门局混算。

### 留存与习惯

必做 D1、D7、D30 三组留存，D0 为首次打开日期：

- 打开留存：第 N 个自然日打开应用的实例 / 对应已成熟新增实例。
- 游戏留存：第 N 个自然日有效游玩的实例 / 对应已成熟新增实例。
- 完成留存：第 N 个自然日完成至少一局的实例 / 对应已成熟新增实例。

“七天内回来过”另称首周返回率，不称 D7。GA4 若不能直接展示严格第 N 天的游戏留存，先用受控测试验证日级用户组探索；仍不能表达时，以本地计算的安装日龄和当日活跃里程碑提供免费替代，并将结果明确标为可观测估算。未正常观察 D0 的实例不加入该计算。不许用滚动留存或第 28 天留存冒充严格 D30。

免费替代需要保留准确的第 0、1、7、30 天分类，其他日期可合并分桶。每日打开里程碑 `app_active_day` 在允许收集后首次打开及前台跨 UTC 午夜时按日去重；游戏用 `game_engaged`，完成用 `game_ended` 的完成结果。默认安装日龄参数随日期刷新，不使用固定用户属性冒充每次事件的日龄。这些事件仅表示当前可观测活跃，不补造缺失日期；新增分母来自同一正常观测用户组，不能用日龄事件总数直接除以当天新增数。

配套必做 DAU、游戏 DAU、WAU、游戏 WAU、30 日 MAU、每人开局和完成数。每周游玩天数分桶、连续用户与七日未活跃后回流用户数尽量完成，先用 GA4 用户组与本地低频汇总实现。

上线前以测试日期和有限的本地时间依赖测试验证口径；生产分析不发送伪造历史时间或虚构用户，不等待真实 D30 数据才发布。

## 游戏体验与难度

| 指标                           | 统计方法                                                | 等级                                    |
| ------------------------------ | ------------------------------------------------------- | --------------------------------------- |
| 各难度开局与完成分布           | 难度使用现有 1–5 级；区分新题与重玩                     | 必做                                    |
| 游戏结果                       | 完成、错误限制失败、明确放弃分开                        | 必做                                    |
| 已结束局完成占比               | 本期完成局 / 本期已明确结束局；注明不是开局用户组完成率 | 必做                                    |
| 明确放弃原因                   | 替换旧局、主动放弃等现有状态，不推测动机                | 必做                                    |
| 完成有效时长                   | 排除后台、暂停和广告，用分桶提供分布                    | 必做                                    |
| 跨日完成                       | 按开始到完成的 UTC 日期差分桶                           | 必做                                    |
| 存档继续与恢复失败             | 成功继续、读取失败、资源变化分别记录                    | 必做                                    |
| 错误、撤销、笔记、快速候选数量 | 本地汇总，结束或片段退出时上报                          | 必做                                    |
| 无提示完成及自动收尾           | 分开标记，不把使用工具解释为成绩无效                    | 必做                                    |
| 同一开局日期组七日完成率       | 需识别跨日同一局；优先有限本地汇总                      | 尽量完成，不能用当天完成 / 当天开局替代 |
| 长时间无填写                   | 仅作为疑似停滞探索，思考和笔记会造成误判                | 尽量完成，不作为失败指标或新增弹窗      |

进入后台、返回首页、操作系统结束进程都不等于放弃。未再返回的局只能标为未观察到后续行为，不能标为卸载或明确放弃。重试同一题建立新的尝试，不冒充不同新题完成。

免费控制台优先显示固定分桶，例如完成时长低于 5 分钟、5–15、15–30、30–60、60–120、120 分钟以上。精确中位数和 P95 若报表无法提供，显示所属区间，不从均值推算。

## 提示与快速候选

提示必做流程为“请求 → 结果 → 有效提示首次展示 → 查看解释或应用 → 关闭”。

| 指标                                 | 口径                                       | 等级     |
| ------------------------------------ | ------------------------------------------ | -------- |
| 提示使用用户占比、每局数量           | 请求与有效使用分开                         | 必做     |
| 首次提示时机                         | 相对游戏有效时长分桶                       | 必做     |
| 有效提示展示率                       | 有效提示首次展示次数 / 提示请求次数        | 必做     |
| 无步骤、棋盘无效、余额不足、计算失败 | 固定结果代码，不上传盘面                   | 必做     |
| 计算耗时                             | 从请求到结果，按难度与结果分桶             | 必做     |
| 解释查看、应用、关闭未应用           | 以已展示提示为分母，同一提示本地去重       | 必做     |
| 各技巧使用分布                       | 复用既有技巧代码，不上传证明内容           | 必做     |
| 提示影响的完成局                     | 游戏结束摘要中记录本局提示次数             | 必做     |
| 提示后继续操作、撤销或退出           | 本地关联短期后续结果，仅汇总，不传操作历史 | 尽量完成 |

提示成功以“有效内容首次展示”计数，只有该动作消费一次额度。同一提示的解释、应用和重复查看不再扣费；冲突、错误、无有效步骤或计算失败不消费。分析事件不得成为扣费依据。

快速候选必做使用用户占比、首次生成、确认重新生成、取消覆盖和失败原因。它对所有玩家免费无限，不再采集旧钱包消费或耗尽流程。高频查看、填写和撤销采用本地计数，避免逐点击上传。

提示后完成率用于观察相关性，不能据此宣称提示造成完成率提升。

## 奖励与额度供需

奖励规则唯一来源为[商业方案](premium-reward-design.md)。以下指标只观察现有规则，不复制或调整福利。

| 指标     | 必做采集                                         |
| -------- | ------------------------------------------------ |
| 奖励来源 | 安装、每日、完成三格补给、广告分开               |
| 每日奖励 | 事务确认后的周期天数、应发、实发和截断量         |
| 连续周期 | 第 1–7 天分布；由本地已有事实判断接续或重启      |
| 提示供需 | 各来源到账总数与有效提示消费总数                 |
| 余额分布 | 使用固定区间，不重复上传完整钱包                 |
| 余额不足 | 用户操作确实被不足余额阻止，不因后台检查重复计数 |
| 容量限制 | 部分到账、零到账、广告容量不足分别记录           |
| 重复奖励 | 本地幂等拦截次数，区分正常重复回调与真实重复入账 |

余额区间固定为 `0`、`1–2`、`3–5`、`6–10`、`11–30`、`31–94`、`95–99`。每日自动到账不是主动签到参与。满仓零到账仍可能是有效周期日；不得以实发大于零才计算连续奖励。

奖励、消费和权益变更以成功的业务事务为准；分析失败不得撤回奖励、重试消费或阻止保存。重复入账属于发布阻断问题，重复分析事件属于数据质量问题，两者不可混淆。

## 自愿激励广告

必做流程为“可用入口实际可见 → 用户点击 → 可用性检查 → 加载与展示 → 有效奖励回调 → 本地到账”。

| 指标                   | 口径                                                     |
| ---------------------- | -------------------------------------------------------- |
| 入口点击率             | 去重点击用户 / 看到可用入口的用户，按实际入口拆分        |
| 展示成功率             | 展示次数 / 用户主动发起观看次数                          |
| 不可用原因             | 离线、隐私、市场、未加载、无填充、SDK 不可用、容量不足等 |
| 加载与展示耗时         | 使用单调时钟计时和固定分桶                               |
| 提前关闭与有效奖励回调 | 分别观察，关闭不等于奖励                                 |
| 到账成功率             | 本地成功入账次数 / 有效奖励回调次数                      |
| 幂等拦截               | 同一广告奖励重复回调的拦截数                             |
| 人数与强度             | 观看用户数、每观看用户展示数、各入口占比                 |
| 收入与广告质量         | AdMob 展示、估算收入、eCPM、匹配率等                     |

入口曝光只记录真实可见状态，同一页面展示期间本地去重；不能在每次 React 渲染时发送。Premium、容量不足或市场与隐私不允许的用户不进入可用入口分母。

AdMob 收入为广告经营来源，不将客户端奖励事件乘固定单价算收入。不新增广告自动播放、额外位置、广告网络或更高频率。广告后继续游玩通过顺序探索或短期本地汇总尽量完成，不建设逐用户追踪后台。[AdMob 报表](https://support.google.com/admob/answer/10979428?hl=en)

## Premium 购买与恢复

必做流程为“Premium 页面可见 → 商品和价格加载 → 点击购买 → 平台返回 → 权益保存并生效”。

| 指标                       | 口径                                               |
| -------------------------- | -------------------------------------------------- |
| Premium 访问与来源         | 实际可见用户，区分设置、额度不足、课程等已存在入口 |
| 商品加载成功率与耗时       | 成功、不可用、失败分别记录                         |
| 购买点击率                 | 点击用户 / 商品可购买且价格已展示的页面用户        |
| 购买结果                   | 成功、取消、待处理、不可用、失败分别记录           |
| 履约成功与耗时             | 平台验证成功到本地权益生效，不用按钮点击代表成功   |
| 新增真实买家               | 首次真实新购，不含恢复、缓存、闭测或审核权益       |
| 7 日与 30 日新用户购买转化 | 已成熟新增实例组的真实购买；用免费用户组探索验证   |
| 恢复购买                   | 恢复、无可恢复、失败、不可用分别记录               |
| 权益刷新                   | 已验证、暂不可用、撤销等结果分开                   |
| 销售、退款、净收入         | 以商店报表为准，不声称客户端可以完整观察退款       |

事件中的权益类别使用免费、真实永久、闭测临时、审核临时、未知。另以功能访问原因区分预发布课程开放，不能将课程开放等同于全量 Premium。离线缓存只有已知真实来源才归入真实永久，否则暂列未知。

Firebase 的自动购买采集与手动收入事件不得重复。上线前沙盒核实实际支持和采集行为，应用自定义 `purchase_result` 只表示流程结果，不再作为收入事件。恢复、重复交易更新、待处理转成功均按业务幂等处理；交易凭证和平台订单 ID 不进入自定义分析。[自动购买采集](https://support.google.com/analytics/answer/9234069?hl=en)

免费与付费用户的游戏表现可比较，但不得将差异直接解释为购买的因果效果。

### 公共维度与数量预算

SDK 已提供的平台、版本、设备和系统字段优先复用。自定义维度首期控制在 30 个以内，自定义指标控制在 25 个以内，为免费标准属性保留余量；实施前列出实际注册清单。

公共自定义字段优先为构建环境、应用语言、手机或平板、当前权益类别、权益来源及功能访问原因。场景字段包括难度、入口、动作、结果、原因、技巧、奖励来源、余额区间、耗时区间、新题或重玩、首局标记、周期天数、正常观测安装日龄区间。

数量汇总使用明确单位，例如毫秒、操作次数、提示次数；通用数量字段只有在事件类型和资源已限定时才求和。游戏片段摘要只上报增量，游戏终态可上报全局总量，两者不能相加计算总用时。片段区间与全局区间分别命名。

游戏局 ID、广告请求 ID、交易幂等键仅用于本地关联，不上传为常规维度。不得注册棋盘指纹、随机 UUID、完整时间戳或用户标识。GA4 高基数字段可能合并为其他行；免费属性当前支持 50 个事件级自定义维度及 50 个事件级自定义指标。[配置限制](https://support.google.com/analytics/answer/12229528?hl=en)，[高基数限制](https://support.google.com/analytics/answer/13331684?hl=en)

### 去重与可靠性

- 新局、游戏终态、首次有效提示、奖励、购买等复用已有业务身份在本地防止重复记录。
- 不在组件渲染或重复订阅回调中直接发业务事件。
- 高频操作在本地累计；摘要只在页面离开、进入后台或不高于每分钟一次的有限检查点发送。
- 计时采用单调时钟；日历口径使用 UTC 日期或已有奖励本地日期，各自独立。
- 先完成游戏和钱包事务，再尽力记录分析；分析异常不得回滚、重做或阻塞业务。
- 不为上报增加无限日志或永久重试队列；如需少量本地去重状态，写入用户数据边界，不写题库。
- SDK 接收调用不等于服务器收到。进程崩溃边界仍可能丢失或重复，普通自定义 `event_id` 不提供通用端到端恰好一次保证。
- 验收要求正常可控路径无可避免的重复；真实财务和奖励事实始终由商店与本地事务确认，不用分析计数对账替代业务账本。

## 离线与隐私

### 离线数据边界

分析初始化、记录和上传不得成为启动、游戏、提示、奖励、保存、恢复或本地统计的前置条件。采集失败自动降级为空实现，核心玩法继续正常运行。

SDK 可缓存离线事件，但不能保证完整还原长期离线历史。Google 当前说明，超过两个自然日加当天才到达的普通事件可能被忽略；迟到 `first_open` 存在特殊处理，行为报告可能采用服务器收集时间。对观测起点异常的安装不承诺精确安装留存。[离线与处理时效](https://support.google.com/analytics/answer/11198161?hl=en)

不通过改写当前时间补报历史开局、重复上传全部存档或自建历史补传服务绕过限制。图表注明可观测样本，离线长时间未回传不能解释为不活跃。

日报保留处理等待期：最近两日标注暂定，主要周判断使用至少经过 48 小时处理的数据；迟到修订仍可能发生，不承诺 48 小时后绝对不变。

### 收集设置与最小数据

- 2026-10-10 产品决定：新安装的使用分析和故障诊断默认开启，取消首次分析询问及设置中的两项开关；此前已保存的关闭选择继续尊重，不强制反转。
- 应用内隐私页在所有应用语言下统一显示单份英文内容（`src/ui/screens/privacy-copy.ts`），保持从左至右阅读；其他界面继续本地化。以简短概括说明游戏使用、崩溃和必要技术信息交由 Google 处理，用于改进体验；不逐项展示事件清单，不宣称完全匿名或完全不处理个人数据。
- 广告同意流程独立保留；UMP 允许广告不等于同意 Analytics 或 Crashlytics。没有弹窗不构成已取得同意，发行前仍须核对目标地区对该配置的要求，隐私说明不替代依法需要的同意。
- Crashlytics 也需禁用未获许可的自动上传与自动行为面包屑，检查原生启动阶段和崩溃后重启的行为。
- 内部关闭设置仍停止采集和发送并按 SDK 能力重置本地分析数据；保留既有关闭值，诊断重新启用不补传关闭期间的报告。
- 停止使用并卸载会停止该安装的后续发送，不代表删除 Google 已收到的报告；隐私政策保留数据请求渠道，无账号与可靠标识时不承诺能定位特定报告。
- 不上传盘面、答案、逐步操作、用户文本、精确位置、通讯录、广告标识符、商店账号、支付凭证或原始订单 ID。
- 不让 Analytics 因现有广告依赖而自动获取广告标识符；分别检查 Android 和 iOS 的最终构建及 SDK 设置，不为分析新增 ATT 或个性化广告。
- 允许的地域分析限供应商已有粗粒度汇总。广告市场门禁继续只按既有商店市场规则处理，不把该市场结果持久化为用户画像。
- 不自行发送 IP；供应商网络处理、自动设备字段及实际关联范围需如实披露，不承诺绝对匿名。
- GA4 事件级探索保留期设为免费能力支持的 14 个月，并核对自动延长设置；它不等于所有汇总报表、Crashlytics 或供应商备份统一 14 个月删除。

Firebase 支持默认关闭和运行时收集控制；具体依赖组合、自动字段、分析本地重置和诊断待发报告必须以集成版本实际验证。[Analytics 收集控制](https://firebase.google.com/docs/analytics/configure-data-collection)，[Crashlytics 收集控制](https://firebase.google.com/docs/crashlytics/customize-crash-reports)，[GA4 保留期](https://support.google.com/analytics/answer/7667196?hl=en)

拒绝收集的用户不会进入行为分母，不能从已同意样本计算全体用户精确同意率。Analytics 首次打开与商店首次打开之比至多是观测覆盖参考，不能称为严格同意率。

| 质量       | 崩溃、存档、启动、提示引擎和设备问题                   | Crashlytics、Android vitals、耗时分桶             |

每张报表记录入口或链接、时间范围、过滤条件、分母、环境和适用平台。未有真实数据时验证配置与测试数据，不填造数。Android 和 iOS 可比较，但不能直接将两平台用户相加宣称独立自然人数。

关键事件只选首次有效游玩、首次完成和真实新购等少量业务结果。首次里程碑采用本地一次性事实，不将每局完成误称首次完成；必要时使用单独的 `first_game_engaged` 与 `first_game_completed` 事件，并纳入实际注册清单。

复杂关联优先使用有限的顺序探索或本地汇总。免费替代无法表达时，记录限制，不显示编造结果，不启用数据仓库。免费 GA4 探索具有采样、保留期和查询限制，控制台采集成功不等于支持任意分析。

## 检查与异常通知

上线前开启适用的免费故障邮件通知和 Play vitals 异常通知，验证收件人和权限。平台不支持自动通知的业务指标，通过保存报表定期人工检查，不为此创建云函数或外部消息机器人。

| 节奏                     | 检查内容                                                   |
| ------------------------ | ---------------------------------------------------------- |
| 发布后每日及新版本观察期 | 新崩溃、无响应、存档失败、权益和奖励入账异常、事件突然消失 |
| 每周                     | 新增、激活、游戏留存、难度、提示、额度与商业转化           |
| 每月                     | 市场与语言、长期留存、广告和购买收入、维护成本及数据质量   |

存档损坏、购买已验证但未生效、实际重复扣费或入账属于立即处理的问题。普通业务指标的波动需要成熟数据、样本量与自身历史比较；不设置无依据的行业留存或收入达标线作为发布门槛。

留存和转化必须显示分子、分母。初始默认样本不足 100 时只作描述，不自动触发百分比波动预警；该值是运营起点，不代表统计显著性。渠道或国家细分还需遵守平台数据阈值。

## 实施顺序

1. 明确公开构建范围、事件契约、免费依赖与测试环境隔离；沿用当前主分支，不新建内容版本或历史兼容支线。
2. 接入 `AnalyticsService` 和诊断边界，完成新安装默认开启、既有关闭选择保留、空实现与离线回退。
3. 接入游戏、新用户、提示与额度，再接广告、购买和公开辅助模块。业务与页面不直接调用供应商 SDK。
4. 配置实际报表、通知和最小自定义维度；同步隐私政策、Data safety、许可与商店披露。
5. 对目标 Release 构建完成真机、沙盒、故障符号、断网和关闭采集测试；再检查尽量完成项的免费替代。
6. 汇总本轮当前验证结果和未完成项，进入发布检查。不保留每次实验的审计档案、数据库或重复证据包。

采用能适配 RN 0.87 当前架构的最小、精确固定依赖。新增库和原生变更需要双平台构建检查，但当前 Android 公开发行只要求其自身生产配置和真机验收完成；iOS 不得因未验证就被标为已具备发行能力。
