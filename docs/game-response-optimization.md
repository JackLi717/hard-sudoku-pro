# 游戏响应优化：第一步

日期：2026-09-03。对照基线：`5e66c36`。

## 改动范围

- 普通填数、候选编辑、擦除、撤销、铅笔模式切换使用顺序输入队列，不再切换全局 busy。
- 填数结果仍然在 SQLite 事务成功后发布。没有采用“先显示、后存盘”。
- 每次输入绑定点击时的目标格；保存中的新选格立即生效，旧保存结果不覆盖新选择。
- 模式切换按队列中的最新已提交状态执行；保存失败时取消依赖它的剩余输入，并显示错误，之后允许重试。
- 暂停、离开游戏、提示和扣费等操作等待已接受的普通输入全部处理，再进入原有操作流程。
- 领域命令输出一次性的 historyChange，数据层仅新增本次 move 或停用被撤销的 move。它不进入持久化协议，没有增加 schema、内容或算法版本。
- 未影响钱包的普通命令不再查询钱包。扣费、结算、事件幂等和 revision 检查仍在原有事务边界内。
- UI 回调保持稳定；格子接收与本格候选相交的数字位掩码，避免全局数组引用变化使 memo 失效。

## SQL 工作量

计数包含事务内的 query/run，不包含 BEGIN/COMMIT。旧基线每次普通操作重置并重新同步全部活跃历史，执行 H + 5 条 SQL。

| 操作 | 基线 SQL | 修改后 SQL |
| --- | ---: | ---: |
| 普通填数/候选编辑，产生第 10 条历史 | 15 | 4 |
| 普通填数/候选编辑，产生第 50 条历史 | 55 | 4 |
| 普通填数/候选编辑，产生第 100 条历史 | 105 | 4 |
| 普通填数/候选编辑，产生第 200 条历史 | 205 | 4 |
| 铅笔模式切换，已有 200 条历史 | 205 | 3 |
| 撤销，从 200 条历史减到 199 条 | 204 | 4 |
| 单纯选格 | 0 | 0 |

100 条历史时，普通输入减少 101 条 SQL（96.2%）；200 条历史时减少 201 条（98.0%）。新流程的四条是查询事件回执、更新会话、新增/停用单条历史、写入事件回执。

## 渲染工作量

棋盘仍完整显示 81 格；下表统计 React 组件函数重新执行的次数，不代表隐藏格子，也不等同于原生屏幕重绘次数。

使用固定测试盘面，显示 51 个候选区，初始选中第 1 行第 3 列。

| 操作 | 基线格子重渲染 | 修改后格子重渲染 | 基线候选区重渲染 | 修改后候选区重渲染 |
| --- | ---: | ---: | ---: | ---: |
| 选第 1 行第 4 列（同行跨宫） | 81 | 26 | 51 | 0 |
| 再选第 1 行第 6 列（同行同宫） | 81 | 14 | 51 | 0 |

跨宫示例减少 55 格（67.9%），同宫示例减少 67 格（82.7%）。修改后重复选择同一格和单纯切换铅笔模式均为 0 格、0 候选区重渲染。

其他选择位置、填数、候选聚焦或提示可能改变更多格子的真实视觉状态，不承诺所有操作固定只更新 14 或 26 格。

## 自动验证

`__tests__/game-response-performance.test.tsx` 挂载完整 HardSudokuApp，覆盖：

- 选格、重复选格、模式切换的格子及候选区重渲染数量。
- cell_first / digit_first 两种模式下，人为延迟首笔保存后继续选格和输入；第二笔输入不丢失、不串格，不显示普通输入加载指示器。
- 暂停等待队列，重启恢复两笔输入与最后选中位置。
- 快速切换铅笔模式、编辑候选、填数、撤销的顺序。
- 保存失败后不执行依赖失败操作的输入，后续可重试。
- 连续 200 次候选编辑的 SQL 上限；模式切换不访问历史表；撤销后新增分支的完整历史恢复；SQLite integrity_check。

`__tests__/sqlite-data.test.ts` 增加增量历史写入/撤销在回执写入失败时的事务回滚测试，验证重试幂等及已撤销 move ID 的冲突保护。已有扣费、结算与提示恢复测试继续适用。

## 性能验收边界

SQL 和 React 工作量可由自动测试确定。Jest 在主机上使用 Node SQLite 和原生 UI mock，不能证明目标手机/平板从触摸到实际显示的端到端延迟。

“95% 的选格和普通填数在 50 ms 内呈现”仍需目标真机 Release 包的输入到呈现测量。模拟器功能通过或主机测试耗时较短，均不能替代这项签署。
